# The management panel and its feed

The management panel is a table under a tab's terminal listing that tab's Claude Code subagents: **Running**, **Planned** and **Done**. It works with no setup — Running and Done come from Claude Code's own data. A manager that knows more (which task each worker holds, what is queued next, when each is due to land, who reviews it) can add that by writing a **feed**: one JSON file per Claude session, described here.

**The pane shows only when subagents are involved**: in a tab whose session has a real subagent — running, or done this session — or whose session is a **manager**, one the manage skill ran in (see **The manager mark**), so its Next up shows before its first spawn. A feed never opens it by itself, and **every row drawn is a real agent** with all its columns: a feed row with no subagent behind it is not drawn (rule 1 of **Merge**), save a manager's own Next up and build rows. A session that is no manager and runs `giverny manage start` for its own sake (a build, a note to itself) therefore shows nothing anywhere.

Giverny ships that manager itself. With `claude.management_panel` on, every Claude session gets a `/giverny:manage` skill (see **The manager plugin**) and a `giverny-manage` command that writes the feed, so Running, Next up with ETAs, and Done need nothing but Giverny and Claude Code: no issue tracker, no `gh`, no scripts of your own. Any other writer that follows this page works the same way, next to it.

**Settings → Management panel** holds everything about the pane: the pane itself (`claude.management_panel`), the manage skill (`management_panel.manage_skill`, see **The manager plugin**), whether every session is given a name (`management_panel.ask_names`, off by default, see **Session names**), one switch per column in the order the pane draws them (`[management_panel.columns]`: `stage`, `id`, `title`, `elapsed`, `eta`, `now`, `tokens`, `usage`, all on by default; a column switched off takes no width, the rest close up and TASK takes the room), the **default lease** and the **limits** (see **Resources**). Every one applies as it is changed. Which **Done** rows show has no row there but is honoured when set by hand in `config.toml` (`management_panel.done_rows`: `"all"` by default, `"hide"`, or `"last"` for the newest `management_panel.done_last` of them).

This document is the whole contract for writing a feed. The reader is `crates/claude/src/feed.rs`; anything this page promises, that module's tests pin.

## Writing it with `giverny manage`

`giverny manage` is the feed writer that comes with Giverny. The plugin puts it on the Bash tool's `PATH` as `giverny-manage`, so a session and its subagents can run it without Giverny being on `PATH`.

```
giverny manage plan  <task> --eta <dur> [--title T] [--note N] [--brief FILE] [--repo R] [--after <task>]  # a Next up row
giverny manage hold  <task> --why "<reason>"  /  giverny manage unhold <task>   # a Next up row waits on the dispatcher, said on the row
giverny manage start <task> [--eta <dur>] [--title T] [--agent <id> [--heavy-ok]] [--repo R]  # Running from now; lands the worker's earlier task
giverny manage eta   <task> <dur left> [--note N] [--why wait|…]                         # re-estimate from now
giverny manage land  <task> [--outcome Done|Blocked|…] [--review TEXT] [--note N]  # Done now; refused while anything of it runs
giverny manage pause <task> [--note N]  /  giverny manage resume <task>          # stop / restart its clock
giverny manage drop  <task>  ·  giverny manage show  ·  giverny manage path  ·  giverny manage clear
giverny manage clear-done                                                        # clear the Done rows
giverny manage name  [<First> | <First Last>]                                    # this session's name, on its status line; none: print it, or draw one
```

- **A session has a name** (see **Session names**). `name` records it beside the feeds, not in one, and `show` prints it first.
- **A task is any short name** (`auth-fix`, `12`). It is the row's `key`. The worker's spawn `description` should name it as a whole word (`auth-fix: fix the refresh race`), which is how the row finds its worker (see **Merge**, rule 3).
- **Every time is measured.** `start` stamps `started`, `land` stamps `ended`, both from the machine's clock when the command runs. `<dur>` is minutes (`25`) or `25m`, `1h30m`, `1.5h`.
- **`start --agent` on a busy worker is a hand-off**. Its Running rows that started five minutes or more before land now (`Done`), so each task keeps its own measured span; rows started less than that before are a batch it was given at once and keep running. The worker's rows are those carrying its `agent_id`, and those with none whose key its spawn description names (a row `start`ed before the spawn gave the id; the plugin's hook also writes the id on such a row at the worker's first tool call). Each row landed so gives its lease back. A `start` with no `--agent` names a worker of the manager session that is idle (all its rows landed, the last within 30 minutes), with the context it carries, as the `--agent` to pass if it takes the task. `start --agent` is the only hand-off: no message to a worker gives it a row, whatever it says.
- **Reuse only a light worker**. Every turn of a reused worker re-reads its whole context, so one deep in it makes its next task slow and dear, and the old context crowds the new task. The limit is one constant, `REUSE_MAX_TOKENS` in `crates/claude/src/manage.rs`: **100k tokens** of context, counted as the TOKENS column and the status line count it (the context of the worker's last API response in its transcript). A plain `start` suggests only an idle worker under it and names the idle ones over it as better replaced by a fresh worker. `start <task> --agent <id>` on a worker over it is refused (exit 1), naming its context, unless `--heavy-ok` is passed; it changes nothing in the file. A worker the row already names is not being reused and is never refused, nor is one whose transcript cannot be read.
- **`eta` takes the time left**, not a total. On a Running row it keeps the figure as `left_s` and when it was given as `left_at` (a pause moves it on, as it moves `started`), and the pane and `show` count down from it by the work done since: an off-clock span (a usage limit, a sleep, an API error) before the figure is in neither, one after it still stops the countdown. It also sets `eta_s` to the wall time so far plus the figure; the first estimate is kept as `eta_first_s`. `start --eta` drops `left_s`: the row counts down from its whole estimate again. On a Planned row it is the new estimate.
- **A planned task never waits silently**. `plan` stamps `planned` the first time. A Next up row may wait on a queued lease (its `claim`), on another task (`plan --after <task>`, which must be a row of the manager session; `--after ""` clears it), or on a hold: `hold <task> --why "<reason>"` writes `held` (refused without a reason, and on a row that is not planned); `unhold` (or `release-hold`) removes it and stamps `unheld`. `start` clears `after`, `held` and `unheld`. `show` adds the wait to the row (`~10m, held: a quiet machine`), and the pane says it in NOW (see **Merge**, rule 8).
- **`eta --why wait`** (or `blocked`) marks the worker as waiting on something that is not the work, from now until its next `eta` without it, a `pause`, or `land`. The span goes to `wait_s` and is left out of the history's working time; the pane's clock does not move. A `pause` closes an open wait, so no span is counted twice.
- **Estimates are told, never corrected**. The figure given to `plan`/`start --eta`, or by a worker's `eta`, is what the pane counts down from (`eta_s`). Beside it the giver may pass `--gut <dur>`, its raw figure before allowing for how far off its gut usually runs; without it the figure counts as the gut figure. Every row that lands (by `land`, or by any other command that leaves it Done) appends one line to `history.jsonl` beside the feeds, or to `$GIVERNY_MANAGE_HISTORY` (set it empty to turn the history off): its `key`, `title`, `repo`, `kind` (the title's leading upper-case type word, as `BUG` in `BUG: …`), `estimate_s` (the guess as given), `gut_s` (the gut figure behind it, kept on the row as `eta_gut_s`), `eta_s` and `eta_final_s`, `wall_s` (from the true start), `paused_s`, `wait_s`, `slept_s` (see **Usage limits**), `work_s` (wall less pauses, waits and sleeps), `told_x` (the factor the dispatcher had been shown when it gave the guess), and `outcome`. `plan` and `start` with `--eta N` then print, under their own line, how far off the giver's *gut* on such guesses has run: the median `work_s ÷ gut` over the newest 20 finished (`Done`/`Review`) tasks of the same repo and kind, else the same repo, else all, needing 5 at a level — plain arithmetic over the file — said in words that carry the direction and held to ×0.2–×3.0 (`or more` when held). `planned auth-fix: ~25m (gut 50m)` and under it `  your gut estimates on BUG tasks in myapp have usually run about 2.1× too high (last 9, median); give your gut figure and the one you settle on: `--eta <settled> --gut <gut>``; with too little history, `  too few landed tasks to tell how far off your gut on such guesses runs (3 in the history)`. How much to allow for it is the giver's judgement. **Why the gut**: scored on the figures as given, the factor undid itself — once givers allowed for it and landed on target, the records came in at ×1.0, the factor drifted to ×1.0, the givers went back to their gut, and it swung back. Learned from the gut it stays as long as the gut is off, and follows it to ×1.0 only when the gut improves. **Lines with no gut** (written by an older version): a dispatcher then scaled its gut by the factor shown, as a rule, so its gut is worked back out as `estimate_s ÷ told_x`; a worker's gut is its figure as given (see the next item). **What counts as shown**: the `plan`/`start` line comes after the figure it is printed with, so the row keeps the line's level (`guess_level`: same repo and kind, same repo, or all) and a figure counts as given under a line once an earlier `plan`/`start --eta` of the same manager session printed that same line; `told_x` is then the factor in effect when the figure is given (what the line would print now), else 1. The row keeps it as `eta_told_x`, set by `plan --eta`, `start --eta` and a dispatcher's `eta` on a row not started yet. History lines with no `told_x` (written by an older version, mostly untold) count as 1. The repo is `--repo`, else the `<repo>` of a `<repo>#<n>` key, else the git checkout the command runs in (a worktree counts as its main checkout). History lines an older version wrote (when `plan` scaled the guess) keep the corrected start figure in `eta_s`; they still read, and the guess is scored from `estimate_s`.
- **The worker's re-estimate is its own track**. The first `eta` on a Running row is kept as `reest_s` with `reest_gut_s` (its `--gut`, else the figure) and `reest_at_s` (working time so far, less pauses and waits), and scored at landing as `(work_s − reest_at_s) ÷ reest_gut_s`. The pane counts down from the worker's figure; its reply echoes the gut figure (`~10m left (gut 7m)`). Later `eta`s are not scored. How far off the worker's gut runs is told only when the worker is asked for a figure, never between asks: in the hook's asks (see the next item), and in the reply to an `eta` given before any ask on the task or without `--gut`. That reply keeps the figure (gut = the figure), tells the line, stamps `track_x` and `reestimate_asked` (so the five-minute ask skips the row), and asks for the figure the worker settles on with the exact command (`giverny-manage eta <key> <settled> --gut <the figure> --note …`); on a first re-estimate it stamps `reest_open_at`, and an `eta … --gut` within ten minutes of it replaces `reest_s`, `reest_gut_s`, `reest_told_x` and `reest_at_s`, so one estimate is scored once. The re-estimate also keeps the factor the worker had been told, as `reest_told_x`: the hook stamps the row `track_x` with each factor an ask tells, and the first `eta` copies the latest stamp (none: 1); it is a record, not used in the arithmetic. **In older versions** a worker was told its factor as information, and the history read each figure as gut × factor; workers mostly gave their gut figure, so each figure read as a gut ×factor too low, the factor told fell further, and the track ran away toward ×0.01. History lines with no `reest_gut_s` therefore count the figure as given as the gut figure. All these fields go into the history. `giverny manage accuracy [--repo R]` prints both tracks — the guess and the re-estimate — for all tasks, each repo and each repo's types with five or more, the older half against the recent half: the instinct (working time ÷ the gut figure, what the line tells), the median ratio of the figures as given (near ×1.00 when the line is allowed for), and their typical miss either way (the median of the ratio or its inverse), so whether the estimates improve is read from the data.
- **The re-estimate ask.** The plugin's `PostToolUse` hook (`giverny hook`, see **The manager plugin**) reads the hook payload on stdin; for a call that is not a subagent's (no `agent_id` in the payload) it delivers the session's messages and renews its leases (see **Resources**), and asks for the estimate of a worker the call just started (see **Agent ETAs**). For a worker's call it finds the dispatcher's feed from the payload's `session_id` and the Running row the worker holds (the row's `agent_id`, else a key its spawn description names). Once the row has run five minutes of working time with no `eta` from anyone, it stamps the row `reestimate_asked` and replies with an `additionalContext` asking the worker, once, to re-estimate with `giverny-manage eta`; when the history has five re-estimates of the same kind it says how far off the worker's gut on them has run and asks for both figures (`giverny-manage eta <key> <settled> --gut <gut> --note "<why>"`). Nothing is put in a worker's context between asks. After that it asks again as each figure runs out: once when the row's `eta_s` has five minutes left (of a figure given with more than five minutes left; a shorter one is asked about only past it), and once when the working time has run past it, the same way and with the same line, never changing the figure. It stamps the row `deadline_asked` / `overdue_asked` with the `eta_s` it asked about, so each figure is asked about once each way and a fresh `eta` starts over. No such ask within three minutes of the last `eta` (`eta_at`, stamped by `eta` and `start --eta`) or of the five-minute ask, nor on a paused row.
- **`land --review "<who> — <what> — <where>"`** writes the row's `review` line and a `landing` of `Review — <who>`. `--outcome` sets the landing word; `--note` is added after it.
- **`pause`/`resume`** write `paused_since`, then move `started` on by the span and add it to `paused_s`, with the true start kept in `spawned`, as **Schema** describes.
- **`pause` stops the clock only, and names what still runs**. Giverny suggests, managers decide: it stops nothing. When the task has `giverny manage run` commands still going (their `.live` records under `runs/`, which keep the command), `pause` lists each under its line, with how long it has run, its pid and the command that stops it — `` `sleep 300`, 8m in, pid 4242: `kill 4242` stops it and all it started `` (a SIGTERM to `run` stops its scope, or run plain its process tree, and still records and releases). Its first line says whether the task is paused: `paused <task>: nothing of <task> runs` when nothing of it runs, else `paused <task>'s clock; …` and that the task is not paused until what it names stops — its worker mid-turn (`its worker <id> is still working (last wrote 20s ago), so <task> is not paused until it ends its turn: tell the user it is paused only then`), its `run` commands, its worker's background shells. A paused row whose worker still works stays under Running, NOW `paused · worker still finishing`; once the worker ends its turn it moves to Next up, `paused since …`, and its manager is told at once, on its next own tool call (a chore, rule 9, `now_paused`, stamped `land_nudged`, told once a pause: Claude Code lists a finished worker for a while, and the end kept is the first): ``Giverny: `g483` is now really paused: its worker has stopped (ended its turn 20s ago). …``, followed by the paused tasks whose workers are still finishing, or ``Giverny: every task you paused has stopped (`g483`, `g485`): you can tell the user they are paused.`` (the app keeps those still finishing as `finishing` in the chores file). A worker that finished before the pause leaves its row `paused · worker finished`, told after the land grace as before. A task still paused ten minutes later with a run going is told to its manager once per pause on its next own tool call (the row stamped `pause_runs_told` with the pause's start), the same list and the same commands.
- **`pause` and `resume` name a worker's own background shells too**. The plugin hook records each Bash call of a task's worker that leaves a shell in the background (its response's `backgroundTaskId`) against the worker's row, in `bgshells/<session>.json` beside the feeds. `pause` and `resume` list the task's shells still running: `` `sleep 600` (shell bjj5phx0d), 40m in: `TaskStop bjj5phx0d` from this session stops it, or `pkill -s 4242` (its shell, pid 4242, and all it started) ``. The registry is the session's, so the manager's own `TaskStop` stops a worker's shell; a pid is named only when certain (exactly one top process holds the shell's output file `…/<session>/tasks/<id>.output`, a session leader whose `eval` is the recorded command). When a worker ends its turn (its `SubagentStop`, let through) with shells still running, its manager is told once, on its next own tool call: "`g472`'s worker ended its turn and is asleep, waiting on 1 background shell of its own still running: `sleep 600` (40m, shell bjj5phx0d). Claude Code wakes it when that ends. …". A call its timeout moved to the background carries `backgroundTaskId` too and is recorded the same way; a shell the hook never recorded (one started before the hook that records shells was installed) is recorded at its worker's `SubagentStop`, from the tool result in the worker's transcript that names it and the payload's registry that has it in flight. A shell drops off when a `SubagentStop` no longer lists it in flight, when nothing holds its output file, or two days after it started. Giverny stops nothing.
- **`land` and `drop` refuse a task that still runs**. A task with anything still running is not done, so both refuse it, for every `--outcome` (Done, Review, Blocked …) and with no override flag, while any of these holds: its worker is mid-turn (its row is Running and its current task, and its transcript was written after its latest finish notice, within the last 15 minutes: a worker quiet longer has gone without a report and holds nothing), or ended its turn asleep on background shells of its own; a `giverny-manage run` command of the task is live; a background shell its worker started is live (the recorded shells above, looked for in `/proc`). The refusal lists each with how to stop it — "its worker … is still working (last wrote 2m ago): wait for its report", `` `sleep 600` (shell bjj5phx0d), 40m in: `TaskStop bjj5phx0d` from this session stops it, or `pkill -s 4242` ``, `` `cargo test`, 8m in, pid 4242: `kill 4242` stops it and all it started `` — exits 1 and changes nothing: the row, its lease and the history stay as they were. Once they are stopped, `land` goes through. A hand-off by `start --agent` (or `eta --agent`) that would land the worker's earlier task is refused the same way while a `run` command or a shell of that earlier task is live; the worker being handed on is not waited for. Giverny gates its own command and stops nothing. **The worker's report** comes first: the plugin's `PreToolUse` hook on `SubagentHandback` (the tool a subagent reports with, measured on Claude Code 2.1.308; its payload carries `agent_id`, `session_id` and `tool_input.message`, no task registry) holds a task worker's report back once per task while a background shell of its own still runs, with the same list and `TaskStop <id>` for each, and says to stop them before reporting; the task is remembered in `bgshells/<session>.held.json`, so its next report goes through, and `land`'s refusal catches what is left. A worker ending its turn asleep on its shells (`SubagentStop`) is not touched.
- **A progress check goes to the manager when a worker runs out of time or asks for more**. Two events, each told once, on the manager's next own tool call or by its `watch`: the worker's figure runs out (its row's clock passes `eta_s`, found off the clock by whoever checks, with no call from the worker needed; once per figure, `overdue_told`), and an `eta` whose finish (now + the minutes left) is later than the finish the figure before implied (the latest `left_s`, else `eta_s`, less the work since, as the pane counts it) by at least 10 minutes and at least 25% of that figure. At most one check per task every 10 minutes (`progress_told`): a later event waits pending on the row (`progress_more`, `progress_overdue`) and further `eta`s fold into it against the same finish before; one that no longer stands (the figure extended, the row landed) is dropped, a paused row's is kept until it runs, and the manager's own `eta <task>` drops that task's pending ask. It reads: ``Giverny: progress check on `g473`: its worker asked for 45m more: finish 14:20 → 15:05. Its note: "…".`` (or ``its worker is overdue by 12m``), then `So far:` the working time, what the worker does now (its last tool call, or `waiting since …`), when it last wrote, its `run` commands and background shells, and its transcript path, then the ask: does it make sense, is it all needed, could it be done faster? Answer it (SendMessage `<agent id>`) or let it go on. A marker `progress/<session>` beside the feeds is there while anything is pending, and `progress/<session>.due` keeps when the next check falls due (keyed by the feed's mtime), so a manager's call costs a `stat` or two and a small read otherwise. Giverny stops, pauses and re-estimates nothing.
- **`watch` brings the progress check to an idle manager**. A hook speaks only on a tool call, and a manager waiting for its workers makes none; but Claude Code wakes a session whose `run_in_background` Bash command ends, idle or not, with a task notification naming its output file. So the manager keeps one `giverny manage watch` running in the background while it has Running rows. It sleeps until the earliest of a Running row's figure running out (`started` + `eta_s`), a pending check's 10-minute quiet ending, or the feed changing (its mtime, and the marker, looked at every 2 s; a new more-time ask is such a change); then it makes the same check the hook makes, prints what is due in the same words and exits. A more-time ask younger than 15 s waits, so that the manager's own `eta` is dropped on its hook first. What the watch told is stamped on the row as the hook's is, so neither tells it again. With no Running row it exits at once, saying so; a second `watch` on the session (`progress/<session>.watch`, held with `flock`, the pid inside) says one is already running and exits. A paused row has no clock: its resume changes the feed. The watch only prints.
- **A worker asleep on its own work reads asleep, not ended**. A Running row whose worker ended its turn while a background shell it started still runs (Claude Code: "is waiting on its own background work … may resume on its own") reads `asleep · wrangler deploy (30m) · wakes when it ends` in NOW (the cell is cut; its hover has it all), `+N` with more shells (the oldest named), and `· waiting: <note>` after it when a wait is open; its hover says since when, each shell in full and that Claude Code wakes it; it is no land chore; and its click follows the transcript live (it goes on when the worker wakes) with the asleep line at the top. The name is the shell's program past its setup (`cd`, variables, `npx`, `giverny-manage run <task> --`, redirections): `cd ~/site; T=…; npx wrangler deploy > $T/d.log 2>&1; echo $?` is `wrangler deploy`. Woken, the row shows its activity again; with no shell of its own left it reads `turn ended HH:MM` as before. **How the pane knows a shell runs:** the recorded shells (`bgshells/<session>.json`, re-read when it changes), each looked for in `/proc` once, when first seen: the processes holding its output file then are its own. After that a poll only asks whether one of them still runs, by pid and start time (a pid that came back as another process is not it). Ended is final, and a look that cannot read `/proc` decides nothing, so a row never flickers between asleep and ended. `resume` says the same: `its worker <id> ended its turn 26m ago and is asleep, waiting on wrangler deploy (30m): Claude Code wakes it when that ends`. Display and wording only: nothing is stopped or woken.
- **`resume` restarts the clock only, and says who works on the task**. Under its line it says whether the row's worker is working (`its worker <id> is working (last wrote 1m ago)`) or ended its turn (its finish notice in the session's transcript is as new as its last turn) and how to wake it: SendMessage to that agent, or a fresh worker with a brief and `start <task> --agent <id>`; a row with no worker says to spawn or hand it on. A wait the worker marked (`eta --why wait`) that is still open is named too: `resume` does not end it (a `pause` closes one; the worker's next `eta` without `--why` ends it). Giverny wakes nothing.
- **The session** is `--session <id>`, else `$CLAUDE_CODE_SESSION_ID`, which Claude Code sets in every Bash command it runs and a subagent inherits from its dispatcher. So a worker that re-estimates its own row writes into its dispatcher's file.
- **The file is the state.** Each command reads the feed, changes one row and writes it back atomically, under a lock (`<session>.json.lock`) so a dispatcher and its workers never lose each other's writes. A file whose bytes would not change is not rewritten.
- **`clear-done` clears the Done rows**: from this session's feed when `giverny manage` wrote it, and from the management panel of the Giverny tab it runs in, whoever wrote the feed. The pane drops its own Done rows, keeps them from coming back from disk, and hides the feed's Done rows that landed before the clear. Running and Next up rows stay. In a Claude session the plugin's `/giverny:clear-done` runs it.
- **It never touches another writer's feed.** It marks its files `"writer": "giverny/manage"` and refuses any file whose `writer` names someone else.

## Resources

Before a worker starts, its manager says what the worker needs, and the **machine ledger** answers. It is one file for every Claude session on the machine, so managers in different tabs, repos and accounts share RAM, GPUs and exclusive slots without knowing about each other. **A lease reserves RAM; CPU is shared and measured**: running out of memory kills a build, running out of CPU only slows everyone, and the kernel already shares the cores, so no manager says anything about CPU.

```
giverny manage claim <task> [--ram 3G] [--gpu N --vram 8G] [--slot NAME]… [--min-ram 2G] [--priority P] [--wait]
giverny manage release <task>
giverny manage resources
giverny manage run <task> [--ram 3G] [--slot NAME]… -- <cmd…>
giverny manage ask <task-or-session> "<msg>" [--task <yours>] [--priority P]
giverny manage reply <msg-id> "<text>"
```

- **`claim`** answers with one line and an exit code: `granted t1: 3G, slot cargo:/x/target` (**0**); `granted smaller t1: 2.5G (asked 3G, more is not free)` (**3**, only with `--min-ram`: less RAM, down to `--min-ram`, when that is what is free; with less free than the floor it queues); `queued #2 for 3G behind demo#12 (3G, slot cargo:/x/target; ~14m)` (**4**: what it is short of, in its own sizes — `3G`, `CPU` (busy, below), `CPU, 3G`, `a slot` — and who is really in the way: the request queued ahead that wants that, since it goes first whatever frees (`behind 899x (queued #1: 3G); held by fold146 (…)`), else the leases holding it — for a busy CPU, the tasks building — with their time left from their own feed rows; a busy CPU adds how busy, `; CPU busy: 7.6 of 8 busy (giverny-claude.slice, last minute; …), 2 tasks building`); `refused …` (**5**: larger than the limits, so never queued). 1 is an error, 2 a usage error. Without `--ram` a claim asks for none (and counts at the default lease). Sizes are `3G`, `1.5G`, `512M`; a bare number is GiB. `--cpu N` and `--min-cpu N`, from an older version, are taken and ignored with a one-line note. A task that already holds a lease is answered with it (exit 0) — unless `--ram` or `--vram` name a smaller figure than it holds and none a larger: then the lease **shrinks in place**, keeping its slots and its place (`shrunk demo#12: 1G, slot cargo:/x (was 3G, slot cargo:/x)`, exit 0), which is how a holder makes room when asked (below). A held lease is never grown by `claim`; release it and claim again.
- **Queued means poll — but the queue moves without you**. The manager re-runs the same `claim` (each run keeps its place alive) until it is granted, or runs it once with **`--wait`** in the background: it prints the first `queued` answer at once (its `ask` hint with it), re-claims every 30 seconds while the answer stays `queued`, and ends on the first other answer — granted, granted smaller, refused, an error — printing it with how long it was queued (`granted t2: 6G (after 4m queued)`) and exiting with its code; its end wakes an idle manager, as `watch`'s does. Every ledger write also moves the queue on, whoever makes it — any session's `claim`, `release`, `land`, `run`, `resources` or heartbeat (so every tool call, through the hook): each waiter that fits, in queue order, by the same rule its own claim would meet, is granted then and there, its lease marked `uncollected`. Its manager's next `claim` answers `granted` (exit 0) as if granted that moment, and `start` or `run` take it up too; its next tool call is told so. A grant nobody takes up within `uncollected_min` minutes in `[management_panel.lease]` of `config.toml` (default 10; no settings row) **lapses**: it is given back and the request returns to its place in the queue marked `lapsed` — dormant, nothing set aside for it, never granted again until its manager claims again — or out, when its session is gone (no claude runs it by Claude Code's registry, and no heartbeat for 5 minutes; a gone session's waiters leave the queue the same way). `resources` and the pane say `granted, waiting for its manager` meanwhile. So a manager that stopped polling — a restart, a crash — no longer freezes everyone behind it. The queue is first come, first served, a `--priority` (`asap` › `high` › `medium` › `low`) ahead of none. A request may go past one waiting ahead of it only with what is left after that one's request is set aside, so a small task can start beside a big one that waits, never take what it waits for.
- **The grant rule.** **CPU is measured, never reserved** (it replaces an older `--min-cpu` and per-kind CPU counting): a claim waits on CPU only while the CPU is **busy** — saturated over about the last minute *and* at least two leases building. Saturated is, on Linux (WSL too), the slice's CPU time over about the last minute at 90 % of its `CPUQuota` or more (from `<ledger dir>/cpu-samples`, the slice's `cpu.stat` counter as recent `claim`s and `resources` saw it) or its `cpu.pressure` `some avg60` at 60 %; on macOS, which has no cgroups, the host's 1-minute load average at 90 % of the limit's cores. Elsewhere nothing measures it and a claim never waits on CPU. Building is a lease with a `run` command going, or one granted in the last two minutes (its build not started, so no measure sees it yet). So one busy build alone never holds the next worker back, nor does load that is not the workers'; a third waits only while two already fill the CPU, where a new build would only split the cores further. Under contention `run`'s scopes split the cores evenly (one `CPUWeight` for all) behind the Claude tabs. Memory is admitted by **expected peaks**, not by the sum of leases: every task counts at the high end of what tasks of its kind peaked at under `run` — the 90th percentile of the same history `claim`'s hint summarises (below), once it has three, but never above twice its lease's RAM, the most a `run` under it can use (its scope's `MemoryHigh`, above which the kernel throttles it) — that bound only where `run` really holds a command to it (a scope, or Giverny's own kill on macOS; `<ledger dir>/run-caps` says which the last `run` did, else the ledger probes as `run` does), and never below what a command still running was started held to (each `.live` file's `bound_mb`), so a lease shrunk under a running command counts at the old bound until that command ends — so the history only lowers what a lease counts at — else at its lease's RAM, else at the default lease; and a task whose commands use more than that right now (their scopes' memory less page cache) counts at that use. A claim fits when its own expected peak fits under the limit less a headroom (5 % of RAM, at least 1 GiB), less what the claudes themselves hold in the slice, less every live task so counted; and under `MemAvailable` less the headroom and what the live tasks may still grow by before their peaks — that is how other programs count: a browser eating 6 G shrinks what is grantable. So oversized leases (3G by default against a typical 1.2G peak) no longer hold memory nobody uses, while tasks are never admitted on the bet that their peaks will not line up. `--min-ram` grants smaller only to a task with no history, which counts at its RAM.
- **A lease's RAM is a protection, not what it is counted at.** It is its `run` commands' `MemoryLow`; the slice's `MemoryMax` is the one ceiling. The leases together may promise more `MemoryLow` than the slice holds: a protection covers only memory in use, and admission keeps what the tasks use (at most their expected peaks) under the limit, so the kernel can honour every protection while each task stays within its history. A task that outgrows it makes the slice tight; the kernel then reclaims from whoever is above its protection, and if it must kill, kills a command (never a claude), which `run` reports and the history learns from. GPU: each GPU asked for has `--vram` free under its limit (leases share a GPU by VRAM). **Slots** are any name (`cargo:/path/to/target` for a shared cargo target dir) and exclusive: one lease holds a slot at a time.
- **Leases expire.** A lease (or a place in the queue) lives 20 minutes past its last heartbeat, and every `giverny manage` command from its session is a heartbeat, and so is every tool call of that session or its workers, through the plugin's hook (below; at most one ledger write per 30 s), so a working manager keeps its leases without trying and a dead one's are dropped on the next read by anyone. `land` and `drop` release the task's lease (even when the task has no row to land; not when they refuse a task that still runs), as does a hand-off for each row it lands; `release` does it by hand. A heartbeat never renews the lease of a task whose row has landed: it drops it.
- **`resources`** prints the machine, the limits (`(auto)` where not set), the default lease, how busy the CPU is (`cpu       6.3 of 8 busy (giverny-claude.slice, last minute; pressure 12%) — shared, not reserved; claims go on`, or `busy: claims wait (2 tasks building)`), the memory other programs leave available, the memory counted against the limit (the leases at their expected peaks or use, the claudes' own, the headroom), what is free now, every lease with what it counts at (`counts 1.3G`) and uses now, its session and time left, and the queue.
- **The feed row carries its lease** as the row's `lease` field (see **Row**), so the pane can show what each Running row holds and which Next up rows wait for resources.
- **The pane draws it**. A row's lease is in the header over its worker (`holds 3G, slot cargo:/x/target`). A quiet last column, after TOKENS, shows what the row's `giverny manage run` commands **use**: on a Running row its use now — ` 14% CPU  ·  4.2G`, CPU as a share of the whole machine (every core busy is 100%) and the memory its scope's processes really use (their proportional sets, shared pages split), summed over the task's running commands, from the app's one reading every second — the same pass the sidebar's tab rows, category headers and total come from, so a row never shows more than its tab. A row's worker's own Bash commands count too, with everything they started, `manage run` or not: the sampler matches each command Claude Code runs to the worker whose transcript has it in flight (the session's own commands, or one in flight in two workers, stay with the session); `0% CPU  ·  0.0G` while none runs — and on a machine with an NVIDIA GPU the GPU memory of the commands' processes after it (`  ·  gpu 1.2G`, from `nvidia-smi`). A Done row shows its memory peak alone (`2.1G`). The column is right-aligned at the end of the pane's table, which is laid out on the terminal's grid, two columns in and as wide as the status line Claude Code draws above it; the status line itself shows no CPU or memory. A Next up row waiting in the ledger reads what its claim said: `queued for 3G behind 899x` or `queued for CPU` in NOW — what it is short of and who is in the way of that. The header adds the measured totals once a run has ended: `peak 2.1G of 3G, 45s CPU`. A run the memory cap killed puts `OOM` at the head of the cell, drawn in the warning (amber) colour, and `OOM-killed x1` to the header — while that OOM is still news: the row's latest run was killed and no fresh grant bigger than that run's cap came since. A later run that is not killed, or a release and a bigger `claim`, clears the mark; the header then says `OOM-killed x1 earlier`, and the history still counts the kill. Only commands run through `giverny manage run` under a systemd scope are measured live; a plain run (no user systemd) shows its use only once it ends. **The ledger decides, not the copy:** the pane reads the ledger itself, off the UI thread, about every two seconds while a pane is up, and draws each row's entry from it — matched by the row's `key` under the feed's or the tab's session ids — so a lease that expired or was released, or a holder that left the queue, is gone from the pane though the row's copy still names it. A queued row is short of what its copy says (its last claim; the ledger keeps no verdict), and is drawn behind whoever is in the way of that now: the first request queued ahead of it that wants it, else a lease holding it. A copy from an older version, which names nothing short, is drawn behind the task it named while that one still holds or waits ahead, else whoever holds a slot it asks for, else the request queued before it.
- **When the ledger is not enough, ask**. The ledger is first come, first served; it cannot know that the holder of `cargo:/x/target` would gladly lend it for a high-Priority two-minute test. So when a queued wait is longer than the task itself — the soonest any holder in the way expects to land, against the asker's own time left (its estimate, for a Next up row), or a holder with no ETA at all — `claim`'s queued answer says so and suggests `giverny manage ask <holder's task> "<why>"`.
  - **`ask`** finds the session holding that task's lease in the ledger (else one queued under that name; or give a session id, or the start of one) and drops a message in that session's **inbox**, `<feed dir>/inbox/<session>.jsonl`, one JSON object per line. The message carries the asker's task (`--task`, else its one place in the queue, else its one lease), what it wants and its place in line, what it holds, its Priority (`--priority`, else its queued request's) and its time left by its own feed row. It prints the message's id (`m` and six characters).
  - **Delivery is the hook.** On each tool call of the manager's own (not a worker's: the lease is the manager's to give), the plugin's `PostToolUse` hook moves the session's unread messages to `<session>.seen.jsonl` (kept a day) and returns them as `additionalContext`: who asks, about which of the session's leases and what it holds, what the asker holds and wants, its Priority and time left, its words, and the three answers — `giverny-manage reply <id> "<answer>"`, `giverny-manage release <task>`, `giverny-manage claim <task> --ram <less>` (shrink in place). A session busy only waiting on its workers sees it on its next own call.
  - **`reply <id> "<text>"`** answers a message (an ask, or a reply), found in this session's inbox files, else anyone's. The reply carries what the asked-about lease holds now, or that it was released, and reaches the asker the same way, with a reminder to re-run its claim.
  - **Messages expire with the asker's entry**: a message is delivered only while the asker still holds or waits for the task it asked for (a message from a session that held nothing lives 20 minutes). Undelivered, it is dropped at the next delivery. A writer other than `giverny manage` may append a line to an inbox under the sibling `<session>.json.lock` (taken with `O_CREAT|O_EXCL`, removed after), in the format `giverny manage ask` writes: `id`, `kind` (`ask`/`reply`), `at`, `from_session`, `from_task`, `to_session`, `about`, `text`, and optionally `in_reply_to`, `holds`, `wants`, `position`, `priority`, `eta_s`, `expires_with` (`{session, task}`).
- **`claim` says what tasks like it peaked at**, once the history has three with a measured peak (`run`, below): `granted demo#12: 3G (the last 4 BUG tasks in demo peaked at 1.8G (median), 2.6G at most)` — the task's repo and title type word, else its repo, else every task. A grant counted at that history's high end says so: `granted demo#12: 3G, counted at its kind's peak 1.3G`; one whose kind peaked past what its lease can use is held there: `granted demo#12: 3G, counted at 6G, the most its lease lets it use`.

**`run`: a worker's command under its lease**. A worker runs its heavy commands — builds, test suites, training — as `giverny manage run <task> -- <cmd…>`. Its own flags go before `--`; everything after is the command, untouched.

- **The cap.** On Linux with a user systemd the command runs in a scope of its own, inside the slice every Claude tab runs in (**Every claude is capped**, below): `systemd-run --user --scope --slice=giverny-claude.slice -p MemoryLow=<ram> -p MemoryHigh=<2×ram> -p CPUWeight=100 -p OOMPolicy=continue`, named `giverny-run-<task>-<pid>.scope` (`systemctl --user status` it while it runs). The grant is a **guarantee, not a ceiling**: the slice is the one hard ceiling, and inside it the command may use idle cores and free memory. Every `run` has the same `CPUWeight` (100), below the Claude tabs' (400), so when cores are contended the builds split them evenly and the person's interactive claude goes first; the grant's RAM is protected from reclaim when the slice is full, and above twice the grant it is slowed (reclaimed), never killed. The command runs with `oom_score_adj` 500, so when the slice runs out of memory it goes before any claude. `CARGO_BUILD_JOBS` is exported unless already set, from the lease's RAM — a job a GiB, at least one, at most the limit's cores (the default lease's RAM for a lease of none) — so more idle cores never push a build past its memory. A lease of no RAM sets no memory guarantee. Without a user systemd (macOS, Windows, a container, `GIVERNY_RUN_NO_SYSTEMD=1`), or when `systemd-run` will not make the scope, the command runs plain and says so; it is still registered as running (`<ledger dir>/runs/*.live`), so the app holds it and the ledger counts it as building. On Linux and Windows the lease's RAM is then advisory. **On macOS Giverny holds it itself** (no cgroups there): it starts at low priority, `taskpolicy -c utility`, so the person's own work goes first; four times a second `run` measures its command's tree (physical footprints) and, once it passes twice the lease (where a Linux scope's `MemoryHigh` would start slowing it; nothing can slow it here) or the limit's RAM if less, kills the biggest process in it and reports an OOM kill (`killed (OOM): its command passed the memory Giverny holds it to on this machine …`); and when no Giverny app is holding it (none in `GIVERNY_PID`), it holds the tree to the limit's cores with a duty cycle (below). `GIVERNY_RUN_NO_SYSTEMD=1` on Linux stands in for macOS, for tests.
- **No lease: claim one.** A task holding no lease gets one claimed by `run` — the **default lease**, 3G unless set otherwise in Settings → Management panel (`[management_panel.lease]`), unless `--ram` says — and `run` gives it back when the command ends. While that claim is queued, `run` polls it every 15 s and the row is *waiting* (as with `eta --why wait`); refused (larger than the limits), the command does not run and `run` exits **5**.
- **Slots are held for the command's life.** For each slot of the lease, `run` takes an exclusive `flock` on `<ledger dir>/slots/<slot>.lock`, so two `run`s under one lease (a worker's parallel commands) take a slot in turn: the second says so and its row is *waiting* until it has it.
- **Heartbeat.** While the command runs, `run` beats its session's leases every 5 minutes, so a long build never outlives its lease's 20 minutes.
- **Live.** While the command runs, `run` keeps `<ledger dir>/runs/<pid>-<n>.live` (`task`, `session`, `pid`, `stats`, `started_ms`, `cwd`, and `bound_mb`: the memory it is held to, null when nothing holds it) and the shim writes its scope's cgroup (`cgroup <dir>`) into the stats file beside it as it starts; the app's sampler finds the scope's processes (`cgroup.procs`) from there and measures them as it measures everything else it shows. (The cap itself, and the peak, stay the cgroup's.) The file goes when the command ends; one left by a killed `run` is skipped and swept by the next.
- **Measured.** When the command ends, `run` prints `exit 0; peak 1.2G of 3G, 45.1s CPU in 30.2s` and adds the run to the row's `usage` (see **Row**). Peak memory is the scope cgroup's `memory.peak` (it counts page cache too), read by a small `sh` shim inside the scope once the command has exited and while the scope still exists; without a scope it is the largest single process's peak RSS (`ru_maxrss`). CPU time is the user + system time of the command and every descendant it waited for. When the task lands, the row's peak, CPU time and OOM kills go into `history.jsonl` (`peak_mb`, `cpu_s`, `oom_kills`), which is where `claim`'s hint comes from.
- **OOM.** A command killed when the slice ran out of memory (the scope's `memory.events` counts an `oom_kill`) is reported (`killed (OOM): the Claude work on this machine together ran out of the memory the limits allow …. Ask for more: …`), so the worker can ask its manager for more RAM and run it again.
- **Exit code** is the command's own, 128 + the signal when one killed it (137 for the OOM killer's SIGKILL). Ctrl-C reaches the command; `run` itself waits it out, so the run is still recorded.
- **A `run` told to go takes its command with it**. Under a scope, a `run` that gets SIGTERM, SIGHUP or SIGINT (a Bash tool's timeout, a stopped worker, Ctrl-C) stops **its own** scope on the way out, as Ctrl-C would stop the command: SIGTERM to every process in `giverny-run-<task>-<pid>.scope`, and 3 seconds later `cgroup.kill` (SIGKILL to each process still listed where that cannot be written); then it releases a lease it claimed, records the run, and exits 128 + the signal (`exit 143 (stopped: run got SIGTERM)`). A signal ignored when `run` started (`nohup`) stays ignored. A `run` that dies with no chance to do that (SIGKILL) is covered by the shim: beside the command it starts a watcher, in a session of its own so a signal to `run`'s process group does not take it, which once `run`'s pid is gone does the same to the scope. Only the run's own scope, found from its own cgroup and only when that is the unit `run` named; any doubt and nothing is signalled. Without this a command that ignores SIGTERM, or a child in a session of its own (a test runner's worker pool), lived on in a scope no lease counted. Run plain (no user systemd, macOS), it does the same to its command's process tree: every process below the command, looked at once a second and remembered by pid and start time, so one that detached from it (`nohup … &`, a double fork) is stopped too and a reused pid never is — SIGTERM, then SIGKILL after the grace. A `run` SIGKILLed while plain still leaves its command running: no shim there to watch it. A command that ends on its own is unchanged: the watcher goes with the shim, and whatever the command left running on purpose (a dev server started in the background) outlives `run` as before.

**Every claude is capped** (Linux with a user systemd; macOS below). The limit holds whether or not an agent remembers `run`. A Giverny tab is a plain shell and stays one; but within a second of a `claude` appearing under a tab, the app's sampler moves that claude, with whatever it has started, into a transient scope of its own, `giverny-claude-<pid>.scope`, inside **`giverny-claude.slice`** (systemd nests it under `giverny.slice`). Everything the claude starts after that is born in the scope: its subagents, every Bash command, every build. The plugin's `SessionStart` hook makes the same move itself as the session starts, before its first command, so nothing the claude starts in its first second is left outside; the sampler's pass then finds it in the slice and leaves it.

- **The slice is the one ceiling**: hard `CPUQuota` and `MemoryMax` (no swap) at the **Limits** below, for every Claude tab and every `run` scope together. It is what keeps the rest of the desktop responsive.
- **A tab's scope holds guarantees**: `CPUWeight` 400, four times every `run` scope's, so the person's interactive claude wins contention against worker builds, and `MemoryLow` = the default lease's RAM (`[management_panel.lease]`). A tab may burst into idle cores and free memory; when cores are contended the CPU splits by weight, and when the slice is full the kernel reclaims from scopes above their protection first. (Weight decides only between processes that wait for the same cores: while the slice's quota, not the cores, is what runs out, the quota goes to whoever runs first. The memory protection counts against the slice's own limit only, since the slices above ours protect nothing.)
- **Commands die before claude.** When the slice runs out of memory the kernel kills the process with the highest badness in it. The sampler gives every process under a capped claude, but no claude, `oom_score_adj` 500 (raising it needs no privilege, and children inherit it), so the runaway command is killed and the session goes on. A Bash command has it from its first instruction: the `SessionStart` hook adds `{ echo 500 > /proc/self/oom_score_adj; } 2>/dev/null || :` to the session's `$CLAUDE_ENV_FILE`, which Claude Code sources in each command's shell; the sampler's raise, up to a second later, covers everything else (an MCP server). `OOMPolicy=continue` keeps systemd from stopping the scope after a kill. The log says each adoption: `claude 4242 in giverny-claude.slice/giverny-claude-4242.scope: weight 400, 3G protected`.

**On macOS Giverny holds the limits itself**. There are no cgroups, so no slice: the app's sampler, the same once-a-second pass, holds what the slice holds on Linux — every claude under a tab with all it started, and every plain `run` command — to the same **Limits**, from what it measures (`libproc`: each process's physical footprint and CPU time), with no privilege:

- **RAM.** When they together use more than the limit's RAM, the biggest command among them is killed (`SIGKILL`), never a claude and never a `run` process — the rule the slice's OOM killer follows. One kill a pass; the next pass sees what it freed. The log says it: `the Claude tabs used 9214 MiB, over the limit's 9011 MiB: killed command 4242 (3120 MiB), the biggest under them (a claude never is)`.
- **CPU.** Every command under a claude is reniced to `nice` 10 (what it starts inherits it), so the person's own work goes first. When they together use more than the limit's cores, the busy command trees (each command a claude started, with all below it, wanting a tenth of a core or more) are held to what is left by a duty cycle, as `cpulimit` does: every 100 ms they run for a share and are stopped (`SIGSTOP`) for the rest, then continued (`SIGCONT`). The share follows their measured demand, at least 5 %; it comes back halfway each second once they fit, and lets go entirely near all of it. Claudes are never stopped, and idle trees (an MCP server, a waiting shell) are left alone.
- **Detached commands stay held.** A process held once stays held while it lives, so a command that detaches (`nohup … &`, a double fork) and is reparented to `launchd` is still counted, as it could not leave a cgroup.
- **What a sampler cannot do** that the kernel does: a command that allocates faster than the looks (once a second in the app, four times a second in `run`) passes the limit before it is killed — by what it grew in that time; a process started and ended between two looks is never seen; a new process runs unthrottled, and at normal priority, until the next look; one that detached before the first look saw it is outside. A command stopped by the duty cycle when Giverny itself is killed (`SIGKILL`, a crash) stays stopped until something sends it `SIGCONT` (`kill -CONT <pid>`); a normal exit continues everything first.

Linux without systemd, and native Windows, get none of this: their claudes run uncapped and the lease is advisory.
- **Leaving the cap is reminded of, not refused** (hooks remind the model to play nicely, instead of Giverny taking charge). The slice's memory cap is the floor that holds whatever an agent does; the plugin only talks. Its `PreToolUse` hook on Bash (the same `giverny-hook`) lets every command run, and when one would leave the cap it adds one line to the session's context: what it is, that it runs outside the tab's limits, and that heavy work goes through `giverny-manage run <task> -- <command>` (with `giverny-manage claim` for RAM) or stays in the tab. **Each kind is said once a session** (kept in `<feeds>/escapes/<session>.json`): a scope or unit of its own (`systemd-run`, `systemctl --user start|set-property|revert|edit …`, systemd `StartTransientUnit` and similar calls through `busctl`/`dbus-send`/`gdbus`), a write into `/sys/fs/cgroup` (a redirection, or `tee`, `cp`, `mv`, `dd`, `mkdir`, `sed -i` and other writers on a path there), `cgexec` and friends, `taskset`, `chrt`, `numactl`, a negative `nice`/`renice`, realtime `ionice`; work handed outside the tab: `wsl.exe` running a command (it starts in `/init.scope`, outside the user manager; `wsl.exe --list`/`--status`/`--shutdown` say nothing), `ssh` to this machine, `docker`/`podman run|exec|start|build|compose up`, `at`/`batch`/`crontab -e|<file>`; and `nohup`/`setsid`/`disown`, which detach work from the session that would watch it. It reads through quotes, `;`/`&&`/`|`, `$(…)`, backticks, `sh -c '…'`, `eval`, `env`/`sudo`/`timeout`/`xargs`/`nice` in front, and a heredoc fed to a shell (`bash <<EOF`, `cat <<EOF | sh`). **Only executed words count**: text a command only mentions — a heredoc's body given to `gh`, a `-F body=@file`, a commit message, `grep systemd-run` — and any read of a cgroup file (`cat`, `awk`, `python` on `memory.stat`) say nothing. `giverny manage run … -- <cmd>` passes, and its `<cmd>` is read the same way. Only in a Giverny tab, where there is a cap to leave.
- **What left anyway is told afterwards, not moved back**. The sampler's once-a-second pass reads the cgroup of every process below a capped claude, and looks once at every other new process: one outside the slice — below a capped claude (`systemd-run --scope` however it was spelled, a script, a program that calls it), or reparented away from it carrying a tab's `GIVERNY_TAB_ID` and a capped claude's `CLAUDE_PID` — is recorded for its session (its `CLAUDE_CODE_SESSION_ID`, else its claude's), the topmost of an escaped tree only, once per process. The session's next tool call or prompt is told, once: `Giverny found a process of this session running outside its tab's limits: pid 4242 'cargo build --release' (in run-u12.scope, not giverny-claude.slice). Yours? …`. A plain shell tab's commands carry no `CLAUDE_PID` and are never found. Not found: `wsl.exe`'s `/init.scope` (no tab's environment reaches it), a `systemd-run` service (the manager's environment, not the caller's), a daemon's children (`tmux`, `sshd`, Docker Desktop's VM).
- **A plugin turned off is accepted, and marked.** `claude plugin disable`, `enabledPlugins` false, `--settings` with `disableAllHooks`, or a claude started before the plugin was written: the session loses the reminders and the session-start adoption, never the cap, as the sampler still moves its claude into the slice within a second. Every plugin hook call of a tab's session leaves `<feeds>/hooked/<session>` (cleared after 30 days unseen); a pane whose session has none 20 s after it was first seen says so first in its footer: `no guard: this session ran no Giverny plugin hook (plugin off, or an older claude); the memory cap still holds`.
- Where there is no user systemd, or `GIVERNY_RUN_NO_SYSTEMD` is set where Giverny starts, nothing is moved and the log says so once.

**Limits** are what *all* managers on the machine together may use. Set them in **Settings → Management panel → Limits**, where each field takes `auto`, a number or size (`6`, `16G`), or a share of this machine (`50%` of the cores or of the RAM, written to the file as the figure it comes to). They are `[manager.limits]` in Giverny's `config.toml`, every key `"auto"` unless set:

```toml
[manager.limits]
cpu_cores = "auto"   # cores − 2, at least 1; or a number
ram       = "auto"   # 70 % of RAM; or "16G"
gpus      = "auto"   # 90 % of each GPU's VRAM (nvidia-smi; none without it); or [{ index = 0, vram = "20G" }], or [] for none
```

**The default lease** is what a task gets when nothing says otherwise: what `run` claims for a task holding no lease. Set it in **Settings → Management panel → Default lease** (each field shows the share of this machine it is); `giverny manage resources` prints it. It is `[management_panel.lease]`:

```toml
[management_panel.lease]
ram       = "3G"
```

A `cpu_cores` there, from an older version, is still read (so the file parses) and counts for nothing.

**The ledger file** is `<feed dir>/resources/ledger.json` (`$GIVERNY_LEDGER` overrides). A writer other than `giverny manage` may read it, and may write it only the same way: take an exclusive `flock` on the sibling `ledger.lock` for the whole read-modify-write, drop expired entries, write to a temporary name in the same directory and `rename` it over. Version 1:

```json
{
  "version": 1,
  "leases": [
    { "id": "5c1e…:demo#12", "session": "5c1e…", "task": "demo#12", "repo": "demo",
      "ram_mb": 3072, "gpus": [], "vram_mb": 0, "slots": ["cargo:/home/me/giverny/.claude/target-shared"],
      "peak_mb": 1229, "granted_at": "2026-10-02T10:00:00Z", "heartbeat_at": "2026-10-02T10:12:30Z" }
  ],
  "queue": [
    { "id": "77d2…:acme#5", "session": "77d2…", "task": "acme#5", "ram_mb": 8192, "gpu": 0, "vram_mb": 0,
      "slots": [], "min_ram_mb": 4096, "priority": "high",
      "queued_at": "2026-10-02T10:05:00Z", "heartbeat_at": "2026-10-02T10:12:00Z" }
  ]
}
```

A lease's `id` is `<session>:<task>`, one per task per session; its `session` is the Claude session to ask for it. `ram_mb`/`vram_mb` are MiB; `peak_mb` (optional, on a lease or a queued request) is the expected peak memory admission counts it at, from its kind's history (held to twice `ram_mb` when that is not 0) — without it, a lease counts at its `ram_mb` (the default lease when that is 0), and `giverny manage` fills it in once the history has one; `vram_mb` is held on each GPU in `gpus`. A lease holds no cores: a `cpu`, `cpu_use_m` or `min_cpu` written by an older version is read and ignored. Timestamps are RFC 3339 (epoch milliseconds are read too). An entry whose `heartbeat_at` is 20 minutes old is gone. A lease granted on another session's call carries `uncollected` (`queued_at`, its `request`, `told`) until its manager takes it up; a queued request whose such grant lapsed carries `lapsed` (`at`, `told`) until its manager claims again. A file of a newer `version` is refused, never overwritten.

## Where the file goes

```
$GIVERNY_FEED_DIR/<claude session id>.json
```

- **`GIVERNY_FEED_DIR`** is exported by Giverny into every tab, so a writer running inside a Giverny tab (or in a hook or subagent of a Claude session running there) just reads it. When it is unset or empty, the writer uses the default: `<config dir>/giverny/feeds`, where `<config dir>` is the platform's config directory — `~/.config` on Linux (`$XDG_CONFIG_HOME` if set), `~/Library/Application Support` on macOS, `%APPDATA%` on Windows. The writer creates the directory if it does not exist.
- **`<claude session id>`** is the session id of the *parent* Claude Code session whose subagents the rows describe — the `session_id` Claude Code puts on every hook payload and on the `subagentStatusLine` input. It is a file name, so use it verbatim.
- One file per session. Giverny never writes, renames or deletes anything in this directory; stale files are the writer's to clean up (or leave — an unmatched file costs nothing).

## Writing it: atomically

Write the whole file to a temporary name **in the same directory**, then `rename` it over `<session>.json`. The temporary name must **not** end in `.json` — use `<session>.json.tmp` or `.<session>.<pid>.tmp` — because Giverny scans `*.json` when it searches by alias.

```python
tmp = os.path.join(d, f"{sid}.json.tmp")
with open(tmp, "w") as f:
    json.dump(feed, f)
os.replace(tmp, os.path.join(d, f"{sid}.json"))
```

Giverny checks the file's mtime and size about once a second and re-reads it only when either changed. A file that fails to parse (a torn write from a writer that skipped the rename) is ignored and the last good read stays on screen, so the worst a non-atomic writer gets is a flicker of staleness — but do the rename.

Rewrite the file whenever anything in it changes. Do **not** rewrite it just to move the clocks: Giverny ticks ELAPSED itself every second from `started` (or from Claude Code's own start time for a live worker).

## Schema (version 1)

```json
{
  "version": 1,
  "session": "5c1e…",
  "aliases": ["0a9f…", "77d2…"],
  "name": "Juniper Belfry",
  "rows": [
    {
      "key": "acme#158",
      "stage": "running",
      "title": "FEATURE: management panel",
      "agent_id": "a93f0c1d2e",
      "started": "2026-09-23T10:00:00Z",
      "ended": null,
      "eta_s": 2400,
      "eta_delta_s": null,
      "landing": "Review — alice",
      "tokens": 123456,
      "group": "lane-1",
      "brief": "/home/me/briefs/acme-158.md",
      "open": "claude --resume 5c1e…",

  ],

```

### Top level

| Field | Type | Required | Meaning |
|---|---|---|---|
| `version` | integer | no (absent = `1`) | The format version; see **Versioning**. |
| `session` | string | recommended | The Claude session id this feed is for — normally the file's own name without `.json`. |
| `aliases` | array of strings | no | Earlier session ids of the same conversation. Claude Code gives a conversation a new id on some resumes and restarts; a tab still holding an old id finds the feed through this list. List every id the conversation has had. |
| `name` | string | no | The manager's name, from before names were kept under `names/` (see **Session names**); still drawn beside the model on the session's status line while names are on. `giverny manage` no longer writes it. |
| `rows` | array of row objects | no (absent = no rows) | The table, in the order the writer wants it drawn within each stage. |
| `footer` | object `{"text": string}`, or a bare string | no | One line drawn under the table, verbatim (a session count, a total). |

### Row

| Field | Type | Required | Meaning |
|---|---|---|---|
| `key` | string | yes, unless `agent_id` is given | What the row *is*: a task id (`acme#158`), a lane name, anything short. Drawn in the id column. When absent, `agent_id` stands in. |
| `stage` | string | **yes** | `running`, `planned` or `done` (case-insensitive; `queued`, `in progress`, `finished`, `completed`, `landed` are accepted as synonyms). Decides the section. A row with no stage, or one Giverny does not recognise, is dropped. |
| `title` | string | no | The row's text — the task title. Without it the pane shows the live worker's own description. |
| `agent_id` | string | no | The Claude Code subagent id holding this row — **the join key** with the live rows (see **Merge**). It is Claude Code's id for the worker: `tasks[].id` in the `subagentStatusLine` input, and the `<id>` in `<config>/projects/<cwd>/<session>/subagents/agent-<id>.jsonl`. Several rows may carry the same `agent_id` (one worker holding several tasks). |
| `started` | timestamp | no | When this row's work started. RFC 3339 string (`2026-09-23T10:00:00Z`, any offset) or integer epoch **milliseconds**. |
| `ended` | timestamp | no | When a Done row landed. Same formats. |
| `spawned` | timestamp | no | The row's true start, when `started` has been moved on by the spans it was paused. Informational. |
| `paused_s` | non-negative integer | no | Seconds the row has spent paused, an open pause counted up to when the file was written. `started` is already moved on by them. Informational. |
| `paused_since` | timestamp | no | Running rows only: the row is paused now, since this instant. Its ELAPSED and ETA hold at the values they had when the file was written (its mtime) — `started` is taken to be true as of then — and NOW reads `paused since 12:58`. A `giverny manage` feed (`writer`) moves `started` only as the pause closes, so its row holds at `paused_since` itself. |
| `killed` | timestamp | no | `giverny manage`, Running rows: when the row was found killed with its session; its clock is stopped at `paused_since`, and NOW reads `killed`. `resume`, `start`, `land` and `pause` clear it. |
| `went_off` | timestamp | no | `giverny manage`: when the row's session last went off with its worker, kept past the revive. A worker that has not written since is dead: `land` and `drop` wait on nothing of it, and `resume` says it was killed. |
| `eta_s` | non-negative integer | no | The estimated total duration of the row, in seconds, measured from `started`. On Running and Planned rows it fills the ETA column (`~1h3m`); on Done rows it is the last fallback the landing is compared against (see **The Done row's ETA cell**). Giverny holds it through a usage limit itself (see **Usage limits**). |
| `repo` | string | no | `giverny manage`: the project the task belongs to, for the history. Informational. |
| `waiting_since`, `wait_s` | timestamp, non-negative integer | no | `giverny manage`: an open waiting span (`eta --why wait`) and the seconds of closed ones. Not drawn; the history leaves them out of working time. |
| `reestimate_asked` | timestamp | no | `giverny manage`: when the hook asked the worker to re-estimate. Informational. |
| `eta_at` | timestamp | no | `giverny manage`: when the current `eta_s` was given (by `eta` or `start --eta`). Informational. |
| `left_s`, `left_at` | non-negative integer, timestamp | no | Running rows: the latest figure a worker gave mid-run, in seconds, and when, on the row's clock. The ETA column is `left_s` less the work since `left_at` — its wall time less usage-limit holds, sleeps and API-error spans — in place of `eta_s` less the work since the start. |
| `eta_first_s`, `reest_s`, `reest_at_s` | non-negative integers | no | `giverny manage`: the dispatcher's figure at the start, and the worker's first re-estimate of the time left with the working seconds it was given at. What a Done row is measured against (see **The Done row's ETA cell**). |
| `deadline_asked` | non-negative integer | no | `giverny manage`: the `eta_s` the hook last asked about with five minutes of it left. Informational. |
| `overdue_asked` | non-negative integer | no | `giverny manage`: the `eta_s` the hook last asked about once the work ran past it. Informational. |
| `progress_more`, `progress_overdue`, `progress_told`, `overdue_told` | object, non-negative integer, timestamp, non-negative integer | no | `giverny manage`: the manager's progress check — a pending more-time ask (`from`/`to` finish, epoch ms, `figure_s`, `asks`, `at`), the `eta_s` a pending overdue check is for, when the task's last check was told, and the `eta_s` last told overdue. Informational. |
| `eta_delta_s` | integer (may be negative) | no | Done rows only: how late (positive) or early (negative) the row landed against its estimate, in seconds. Send it only when you know better than Giverny's own arithmetic — e.g. a usage-limit wait that should not count. See **The Done row's ETA cell**. |
| `landing` | string | no | Where the row lands or landed — `Review — alice`, `Done`, `Blocked`. Drawn verbatim. |
| `tokens` | non-negative integer | no | Tokens spent. A live worker's own count takes precedence; this is the fallback (a Planned row has none; a Done worker Claude Code has forgotten still has this). A Done row of a worker that took tasks in turn shows its task's own count instead (**Merge**, rule 7). |
| `task_tokens` | non-negative integer | no | Done rows: what the task spent, frozen when it landed. `giverny manage` writes it on a row whose worker held other tasks before or after it: the worker's transcript turns from the row's start (the worker's first turn, for its first task) to `ended`, counted as rule 7 counts. Another task is one begun five minutes or more apart, or one that landed before the other began, however short. Drawn in place of any other count. |
| `group` | string | no | A lane or batch name. Informational; Giverny may draw rows of one group together. |
| `brief` | string (absolute path) | no | A file shown read-only when a **Planned** row is clicked, as the worker's prompt on its worker page. |
| `open` | string (shell command) | no | Run in a new tab when a **Running** or **Done** row is clicked, in place of Giverny's own transcript view (`giverny transcript --follow <agent jsonl>`) — e.g. `claude --resume <id>`. A command that resumes a conversation something is already running is not run: Giverny switches to the tab holding it, or says so. |
| `note` | string | no | Free text; shown, with the row's key and title, for a Planned row with no `brief`, and as a tooltip otherwise. |
| `review` | string | no | Done rows: the one line a person has to read before the row counts (`<who> — <what> — <where>`). It is shown in the header over the row's worker page, verbatim. See **The Review line**. |
| `usage` | object | no | `giverny manage run`: what the task's commands used, measured — `runs`, `peak_mb` (the highest peak of any run, MiB), `cpu_s` and `wall_s` (summed), `oom_kills` (every kill, for the history), `oom_open` (the latest run was OOM-killed and no grant bigger than its cap came after it — what the pane's `OOM` mark follows; a row from before it reads open only when `last_exit` is 137 with a kill counted), and the last run's `last_cmd`, `last_exit`, `last_peak_mb`, `last_at`, `capped` (held by a systemd scope) with its `cap_ram_mb` (a `cap_cpu` from an older version is ignored). Kept on the Done row; its peak goes into the history at landing. See **Resources**. |
| `planned` | timestamp | no | `giverny manage plan`: when the row joined the plan. A Next up row with it can be flagged as idle (**Merge**, rule 8). |
| `after` | string | no | Planned rows: the key of the task this one waits for (`plan --after`). Drawn `after <key>` in NOW until that row is Done. |
| `held` | string | no | Planned rows: why the dispatcher holds it (`hold --why`). Drawn `held: <why>` in NOW, in full in the header over the worker. |
| `unheld` | timestamp | no | Planned rows: when the last hold ended (`unhold`). The idle clock starts there. |
| `lease` | object | no | `giverny manage claim`: what the machine ledger answered the row's task — `state` (`granted`, `smaller`, `queued`), `ram_mb`, `gpus` (indices), `vram_mb`, `slots`; granted rows add `id` and `granted_at` (and `smaller` ones what they asked: `wanted_ram_mb`), queued rows `position`, `behind` (the holder it waits on) and `short` (`cpu` for a busy CPU, `ram`, `gpu`, `slot <name>`). A `cpu` or `wanted_cpu` from an older version is ignored. For a queued row the figures are the request. A copy as of the last `claim`, removed by `release`/`land`; the ledger is the truth. See **Resources**. |

Timestamps and numbers are forgiving: a number sent as a numeric string (`"2400"`) is read, a fractional number is truncated, a negative `eta_s` or `tokens` reads as absent. `null` is the same as leaving the field out.

## Merge with the live rows

Claude Code reports each live subagent itself (id, name, status, start time, tokens, what it is doing now), and Giverny keeps the ones that finished until the tab's `/clear`, a `giverny manage clear-done`, a fresh `claude` started in the tab, or a `/resume` into another conversation, which shows that conversation's own workers instead. A re-id of the same conversation — the agents view's ← →, the move into a background host, a compact — keeps them. Those are the **live rows**. The feed's rows are joined to them on **`agent_id` = the live row's subagent id**:

1. **Every feed row a worker stands behind is drawn** (rules 2 and 3), in feed order, in the stage the feed gave it. The feed's stage wins over the live one: a worker that holds two tasks may have one Done and one still Running. **A feed row no live row carries is not drawn** — a feed row annotates a worker, and alone it would be blank where the worker's cells go — except in a **manager** session (see **The manager mark**): there its Next up rows (a Running row with no worker is drawn under Next up, rule 9) and its build rows — a row with a `lease`, a `usage` or a run going (`giverny manage run` on a row of its own, `integ-build`), in any stage — are drawn with no worker. What a Next up row waits for (rule 8) is still read off every row, drawn or not.
2. **A feed row whose `agent_id` matches a live row carries both.** The feed supplies `key`, `title`, `started`, `eta_s`, `landing`, `brief`, `open`; the live row supplies the clock's start, tokens and the current activity — the first two exactly as Claude Code's own agents view has them, so the two agree. The clock counts from the worker's `startTime`, not from `started`, which a writer stamps a little before the spawn; `started` counts only for a row that began more than five minutes after its worker did (a later task given to the same worker), and a row's pauses move the worker's start on by as much as they moved `started` on (`started − spawned`, else `paused_s`). A row that began more than five minutes before its worker did (a fresh worker taking a task over, often after a pause) counts from `started`: its pauses came before that worker, and the worker's start moved on by them would lie ahead and hold the clock at 0:00. Tokens are Claude Code's `tokenCount` — the context of the worker's last turn plus all its output so far — read from each tick, with the transcript's context (re-read every second) as the floor: Claude Code's count is only ever below it when it is wrong, as after an API error, where it is the worker's output alone. Where both have a value, the live row's tokens win over the feed's `tokens`.
3. **A feed row with no `agent_id`, or one Claude Code no longer lists, is joined by its `key` instead**: to the live row whose spawn `description` names the key as a whole word (`Work demo#82 open direct` names `demo#82`, never `demo#820`). A description naming several keys is one worker holding each of them. A Running row takes a worker still running where there is one, any other row a finished one. So a writer that could not know the worker's id when it wrote the row — it wrote at spawn time and nothing has rewritten it since — still gets one row with the worker's tokens and activity. A row that matches nothing either way has no worker (rule 1): in a manager session, a Next up or build row is drawn as the feed wrote it, its clock from `started`, its tokens from `tokens`; any other is not drawn.
4. **A live row no feed row carries is drawn on its own** — unless its description names a feed row's key, in which case it is that row's worker and is never drawn a second time. It is drawn as Running or Done by its own state, after that stage's feed rows. So a feed that describes only some workers leaves the rest visible.
5. **Sections are drawn Running, then Planned, then Done**; order within a section is feed order, then unmatched live rows in Claude Code's order — except **Next up, which reads in the order its rows will start, the next on top**, by what each waits for (rule 8): first a row that waits only for its worker (its lease granted, taken up or not, or a Running row with no worker, rule 9); then rows queued in the machine ledger, by their place in its queue; then rows with nothing recorded to wait for; then rows `after` another task, below that task when it is in Next up too, chained; held and paused rows last, with whatever waits on them. Rows that wait alike keep feed order (the plan's), so across managers the ledger's queue decides.
6. **Dittos:** a row whose worker (`agent_id`) is the same as the row directly above it, in the same batch (rule 7), draws its per-worker cells — agent, ELAPSED, tokens, activity — as `"`. Give a worker's rows adjacent positions in `rows` to get that.
7. **One worker, tasks in turn**. A worker given its next task (`start <next> --agent <worker>`, then its brief by `SendMessage`) holds a row per task, each with its own clock and its own tokens. A worker's Running and Done rows are grouped by when they began: rows that began within five minutes of each other are one **batch** — the tasks it was given at once (`Work #144 #145`), one clock and one count, dittoed — and each later batch is the task it was handed next.
   - **Each task closes the one before.** A row of an earlier batch ends where the next batch began, at the latest; a row still `running` in the feed is drawn Done there, its NOW cell `→ <next key>` unless it has a `landing`. So `start <next> --agent <worker>`, run before the message is sent, is the whole hand-off; `giverny manage start --agent` also lands the worker's earlier Running rows in the file.
   - **When a task began.** A row the spawn named (its worker's description names its key) began with the worker. A later one began at its `started`, which `start --agent` stamps at the hand-off.
   - **Tokens per task.** A Running row always shows the worker's live count, the context it works with now, as Claude Code's agents view shows it and `giverny manage start` says an idle worker carries, whether the worker is fresh or reused for a later task. Every Done row of a worker with more than one batch shows only what its task added: over the worker's transcript turns from its batch's start (the first batch from the worker's first turn) to the next batch's, each reply once, its output plus the input read fresh (uncached input and cache creation; cache reads are carried context). A worker's Done rows add up to what those tasks added, nothing counted twice. Where the transcript cannot be read a Done row's cell is blank, never the worker's whole count again. A Done row's `task_tokens` (written by `giverny manage` when it landed) is drawn in its place: the count stops where the task did. The worker's start for all of this is its spawn — the earlier of Claude Code's `startTime` and its first turn — since Claude Code lists a worker woken by a message afresh, `startTime` moved to that message.
   - **A message hands nothing over**. The dispatcher's messages in the worker's transcript are read for nothing: a row is a worker's only by its `agent_id` (`start --agent`) or the worker's spawn description. A row handed on with `start --agent` and no worker yet is the worker's all the same; one `start`ed with no `--agent` and never handed on has no worker (rule 9). A worker woken by a message is listed afresh with its `startTime` moved to the message, and that counts as it working: its earlier finish notice does not land it again before its next turn, so its row stays Running.
   - **Queued on a worker.** A Planned row whose `agent_id` names a worker running another task says `after <that key>` in its NOW cell.

   The status line's `subagents` and `total` are per agent, each transcript read once; they are never the rows added up, so none of this changes them.

8. **A Next up row says what it waits for**, first that applies: `held: <why>` (its `held`); `queued for 3 cores behind 899x` (a queued `lease`: what is short, and who is in the way); `after <key>` (its `after` row, while that is not Done; a key the feed lacks is no wait), or the task its worker is busy with (rule 7). A row with none of these is free to start, and is drawn as any Next up row, NOW empty: starting it is its manager's chore, not the person's. Once five minutes (`IDLE_PLANNED_MS` in `crates/claude/src/manage_chores.rs`) have passed since the latest of its `planned`, `unheld`, its `after` row's `ended` and its lease's `granted_at`, its manager session is told once, on its next tool call (rule 9). A row with no `planned` (another writer's) never is.
9. **A manager's chores go to the manager**. Chores are worked out only from the rows the pane draws: a session with nothing drawn hears nothing, and one that is no manager never draws a row with no worker, so it is never told "no worker". A manager still is: its Next up draws such a row, and the chore catches a manager that ran `start` and forgot to spawn. Three rows are the dispatcher's to act on, never flagged for the person: a Next up row idle as in rule 8, a Running row with no worker (below), and a Running row whose worker has finished (handed back, failed, killed or stopped) and that nobody has landed — drawn as any Running row in its own colour, a click still opening its transcript, its NOW saying when the worker's turn ended and the wait it marked, if one is open (`turn ended 11:41 · waiting: machine time`); its hover adds that nothing works on it until its manager wakes the worker or lands it, and the wait in full. The app works both out from the very rows the pane draws, for every tab whose session is up, every ten seconds, and keeps the due ones in `<feed dir>/chores/<session>.json` (present only while one is due). The plugin's `PostToolUse` hook, on the dispatcher's own calls (never a worker's), hands each to the session as one line of context — `` `demo#7`'s worker finished 4m ago: check its report and `giverny-manage land demo#7` ``, `` `demo#8` has waited 12m with a free lane: start it, or `giverny-manage hold demo#8 --why "<reason>"` `` — and stamps the row (`land_nudged` / `start_nudged`, the instant it became a chore), so each is told once; a row that becomes one again from a new instant (a worker messaged again that finishes again, a hold that ends) is told again. A finished worker's row is due three minutes after the worker's end (`LAND_GRACE_MS`): the dispatcher hears of the end at once and usually lands within a turn or two. Only an end after the row was handed to that worker counts: a task given to an idle worker (`start <key> --agent <id>`) is not finished by the end of the task before it. Until the worker picks it up the row is no chore and is drawn plain; if it has not been picked up three minutes after the hand-off, it has no worker. **A task nobody works on is Next up, not Running**: a Running row with no worker three minutes after it started or was handed on (a spawn or a pick-up would have come by then), one its manager paused or held with no worker on it (at once), or one whose worker handed it back and that its manager paused or held rather than landed, is drawn at the head of Next up, its NOW saying why — `held: <why>`, `paused since 10:42`, `no worker yet` — with a Next up row's cells (no elapsed time, `~` its estimate). The file still says Running and its clock keeps the pause rules; a worker picking it up draws it Running again. One not paused or held is a chore too: `` `demo#9` is Running with no worker (7m since it was handed out): spawn one for it, hand it to an idle one (`giverny-manage start demo#9 --agent <id>`), or `giverny-manage pause demo#9` / `giverny-manage drop demo#9` ``, due three minutes after it was handed out (`HANDOFF_WINDOW_MS`) and stamped `worker_nudged`; paused, held or landed by then, it is never said. What stays flagged in the warning (amber) colour, for the person, is a worker stopped on an API error (`stopped: <reason>`); a worker that failed or was killed keeps its row Running, its end in NOW (`stopped: failed`).
10. **An agent a worker spawned hangs under that worker's row**. Claude Code lists every agent of the session, a worker's own agents too, flat; only the agent's `agent-<id>.meta.json` names its spawner (`parentAgentId`, with `spawnDepth`), and Giverny reads it once per agent. Such an agent is drawn right under its spawner's row, its title indented a step per level (`└ Triage group A`), with its own stage, clock and tokens, and goes wherever that row goes, Running or Done — a Done worker's agent still running stays under it. A worker holding several rows takes it under the one whose task was under way when it spawned it. A worker's tokens are its own context only; its agents' are on their own rows. The worker's row carries a toggle at the head of its title: `▾` folds its agents away (in Running and Done alike), `▸` shows them again, and a folded row says what it hides, `+6, 2 running`. In a narrow pane nothing on the row overlaps: the title gives way first, down to a few cells, then the note shortens to `+6`. TASK never gets narrower than the id, the nesting, those few cells and the short note, so past that the table runs off the right instead. The fold is kept per tab for as long as Giverny runs. A click anywhere else on a nested row opens it as any worker's row: Claude Code's agent strip lists nested agents too, so a running one is walked into, a finished one's transcript opens. A nested agent is a feed row's worker only by `agent_id`: its description, which may well name its worker's task, never makes it one (rule 3). An agent whose spawner has no row on the pane is drawn on its own, as before. `done_rows`' `last N` counts only Done rows of their own; what hung under a Done row it drops goes too, but an agent still running there is drawn on its own.

`aliases` are not part of the row merge; they only decide which file belongs to a tab. Giverny looks for `<current session id>.json` first, and if there is none, for the most recently modified `*.json` whose `session` or `aliases` contains the current id. If none does, it tries the tab's earlier ids the same way, newest first, so a session Claude Code just re-id'd keeps its rows.

`giverny manage` keeps a conversation in one file across those re-ids. Each file it writes records its transcript's root record (`root`, the `uuid` of its first turn, which Claude Code copies forward under a new id). A session that no file names yet adopts the file whose root is its own. The file keeps its name, the new id becomes its `session`, and the old one moves to `aliases`, so the plan, the clocks and the history carry on. `/clear` starts a new root, and so a new file. The agent-ETA files below work the same way.

## Agent ETAs

A worker that is no manager session's task — a plain session's batch of workers, an Explore search, a helper — has no feed row, and its estimate lives apart from any feed: `<feed dir>/agent-etas/<claude session id>.json`, keyed by the agent id Claude Code gave the worker. It holds an estimate and when it was given, nothing else: no task key, no landing, no history.

```json
{ "version": 1, "session": "<id>",
  "agents": { "a1b2c3": { "left_s": 480, "at": "2026-10-06T10:06:30Z",
                          "first_left_s": 480, "first_at": "2026-10-06T10:06:30Z" } } }
```

- **Whoever spawns a worker estimates it.** Right after a dispatcher's `Agent` call starts a worker in the background, the plugin's hook asks the dispatcher, once per worker, for its estimate, unless a manager session's row holds the worker (its `agent_id`, or a key its description names) or the file has one for it already. The dispatcher answers with `giverny eta <agent-id> <minutes>` (`giverny-eta` from the plugin), the time left from now. Each worker gets its own figure; none is copied from another.
- **The worker re-estimates it.** Five minutes after its spawn (its `agent-<id>.meta.json`'s mtime), the hook asks the worker, once, to estimate the time left with the same command, saying what the pane shows now, or that it has no estimate yet. One that gave a figure past its five minutes already is not asked; the ask is marked under `agent-etas/asked/<agent id>` (holding when it was made), pruned after a day.
- **And again as each figure runs out.** Once five minutes are left of the worker's current figure (one given with more than five minutes left), and once when it has run past it, the hook asks the worker the same way, saying how far along it is. Each figure (its `at`) is asked about once each way, marked in `agent-etas/asked/<agent id>.deadline` (`<at ms> near` or `<at ms> past`); a fresh `giverny eta` starts over. No such ask within three minutes of the figure being given or of the five-minute ask, or before the five minutes. A worker spawned in the foreground blocks its dispatcher until it is done, so these asks are the only ones it gets.
- **Only where something shows the worker**: in a Giverny tab, or in a session with a manager session. Anywhere else the hook asks nothing.
- **The pane** draws such a worker by its description, with no id in TASK, and counts down from the time it had run when the figure was given plus the figure. A Done row's ETA cell is how it landed against that. A feed row that holds the worker wins: its key, its estimate.
- **A row a worker started itself** under the first version of this (key `agent-<id>`, `follows_worker`) is drawn with no id too.

## Usage limits

While the tab's account is out of a usage limit — Giverny's own meters show a window at 100% with a reset still to come, or the tab stopped on a limit message — nothing runs, so the pane holds every **Running** row's clock: ELAPSED stops, the ETA stays where it was instead of counting down past zero, and NOW reads `5h limit → 13:00` (`7d limit → Mon 08:00` for a reset on another day, `limit` when nothing says when). Once the limit clears both clocks carry on from where they stopped: the span out is taken off the row's ELAPSED for as long as the pane remembers it (while Giverny runs). Planned ETAs are durations and do not move. A Done row is measured history and is left as it landed. A writer does not need to do anything for this. A writer that pauses rows itself for the wait (moving `started` on, with `paused_s`/`paused_since`) may: a row carrying either field is taken to have its stops in `started` already, and the pane's own hold is not applied to it again.

Nor does anything run while the machine sleeps. With the pane on, Giverny keeps a thread that naps five seconds at a time and reads the wall clock on each side; a nap that comes back more than a minute late was a machine that ran nothing — a laptop asleep freezes WSL's VM — and the span goes onto `sleeps.jsonl` beside the feeds, one `{"since":…,"until":…}` line (epoch ms) each. Every clock takes those spans off: a Running row's ELAPSED and ETA (whoever wrote the row, pausing or not), a Done row's ELAPSED and its `(+5m)`, and `giverny manage`'s own: `show`, a re-estimate's `reest_at_s`, and the history's `work_s` (the span is its `slept_s`). A sleep inside a usage-limit hold comes off once.

Nor while Giverny, WSL or the manager session is off. A worker is a subagent of its manager's `claude`, so a Giverny close, a `wsl --shutdown` or a crash takes it too, and a Running row would come back hours older. The plugin hook already tells the manager session it was restarted or rebooted on its next call (`away.rs`); at that moment `giverny manage` stops every Running row of the session that is not paused already: an open pause from the session's last sign of life (the latest of its last hook call, its Running rows' workers' transcripts last written and their last measured `run`s: the workers died with it) with `killed` stamped beside it. NOW reads `killed`, under Running; ELAPSED and the ETA stand where they were when it went off; the row asks nothing of its manager (no land chore); and the manager hears which rows were killed. Only the manager revives one: a fresh worker whose description names the task (or an idle one, `start <task> --agent <id>`), then `giverny manage resume <task>`, which restarts the clock from there; or `pause` (set aside, reads `paused since …`) or `drop`. The off span and the wait for the revive are a pause: out of the row's clock, its countdown and the history's `work_s` (in its `paused_s`). Like a finished one, a killed worker gives its row to a fresh worker spawned after it whose description names the task, the one a click on the row opens and types to. A sleep kills nothing: its processes lived on, and its span comes off as above.

## Stopped workers

A worker that stops on an API error — no network (`EAI_AGAIN`), a usage limit, an expired login, a timeout — writes Claude Code's `<synthetic>` `isApiErrorMessage` line as its last turn. From that line on its **Running** row stands still: ELAPSED and the ETA hold, and NOW says why (`stopped: no network`, `stopped: usage limit`, `stopped: login expired`, `stopped: timed out`, `stopped: API error`). The same holds for a Running feed row whose worker Claude Code reports failed, killed or stopped (`stopped: failed`, …). A worker that finished cleanly is not held: its manager's landing is still time on the task. When the worker is continued — Claude Code lists it running again, or it writes its next real turn — the clocks carry on from where they stood, with the stopped span taken off ELAPSED for good (the spans are saved with the row, so a restart keeps them). A writer does not need to do anything for this.

## The Done row's ETA cell

A Done row has nothing left to estimate, so its ETA cell says how the landing compared with the estimate: **`(+5m)`** landed five minutes late, **`(-1h20m)`** landed an hour twenty early, **`(±0m)`** on the minute. It is blank when there is no estimate.

- If the row has **`eta_delta_s`**, that is the value.
- Otherwise it is measured against the **worker's first re-estimate** when the row has one (`reest_s`, given at `reest_at_s` of working time): **`(work − reest_at_s) − reest_s`**. Not the latest figure: one given five minutes before the landing says nothing of how the estimate went.
- Without one, against the **dispatcher's figure**: **`work − eta_first_s`**, else `work − eta_s`.
- The work is the row's clock (the worker's start, else `started`, to `ended`) less its waits (`wait_s`) and what the machine slept through: as the history's `work_s`, so the cell and `giverny manage accuracy` score the same pairs. If `ended`, the estimate or both start times are missing, the cell is blank.
- The header over the row's worker says which figure it was: `(-5m) vs worker's 30m`, `(+15m) vs estimate 20m`. A worker no feed row carries is measured against its agent ETA's first figure.

Durations everywhere in the pane are written the way the ETA column writes them: whole minutes (rounded), units that are zero left out — `5m`, `1h3m`, `1h`, `1d3h12m` — with `~` in front of an estimate and none on a measured span.

## What a click on a row opens

A click on a **Running** row whose worker is mid-turn opens Claude Code's own view of that worker in the tab. Every other row opens Giverny's **worker page** in the same place: a worker whose turn has ended (finished, or asleep on a background shell of its own), a **Done** row and a **Next up** row. Claude Code keeps no view of those, so Giverny draws one as Claude Code would, and it takes the tab the way the running view does:

- It fills the terminal's area, in the terminal's own grid, font, colours and worker background, with the worker's prompt on its grey band and each entry under it.
- Claude Code's prompt box follows, its rules in the worker's colour and the task's name on the top one. No key reaches the shell under the page.
- **Typing in that box goes to the manager**. Claude Code cannot be typed to about such a worker, but its manager can wake it (`SendMessage`), or start a Next up task. On Enter, Giverny puts one plain line at the manager's prompt and submits it: `Send this to g477's worker (agent <id>): <text>` for a worker whose turn ended (finished, asleep, or Done), or `Start g483 now, adding this to its brief: <text>` for a Next up row. The text is only what the user typed; nothing else is ever sent, and nothing is sent without their Enter. The manage skill tells the manager what each line means and that it is the user's.
  - The line is typed only into the manager's main prompt, and only when that prompt is empty. A tab on a worker's view is walked back to main first, and the line is read back off the screen before Enter goes. **A draft of the user's in the manager's prompt is never typed into**: the line is refused, put back in the page's box, and the page says why under it. A busy manager queues the line as Claude Code queues anything typed during its turn.
  - Once the line is in, the page says so and waits. When the worker it named runs again (or, for a Next up row, the task's worker has started), the page gives way and the tab walks into that worker's own Claude Code view, as a click on a Running row does. It does so only while the page is still up in the tab in view; left, the wait ends, and the row is Running again by itself.
  - A landed task is put back in Running by the manager's `giverny-manage start <task> --agent <its worker's id>`; the time it sat landed is left out of its working time. A Running row whose worker had finished is Running again as soon as the worker is, with no command.
  - Esc clears a line in the box; on an empty box it goes back.
- A page with nobody to send to (a note, a worker Claude Code still lists) keeps the box dimmed and `read-only`.
- The same header sits over it as over a running worker's view: the task's name alone (`g477`, never the description after it), the row's facts and a Done row's Review line.
- The same "back to manager" button sits under the prompt box. It, Esc, or a second click on the row goes back to the terminal.
- The wheel, PgUp/PgDn and Home/End (with the box empty) scroll it, and a drag selects and copies. A worker still writing is followed as it grows, a Done one opens at its end, and a Next up row's brief, drawn as the worker's prompt, opens at its top.

## The Review line

When a **Done** row is clicked, the header over its worker page can carry one line saying what a person has to look at before the work counts.

That line is the row's `review` field, shown as written. The manager writes it with `giverny manage land <task> --review "<who> — <what> — <where>"`. A row without one opens with no Review line. Giverny does not look the line up anywhere else, such as an issue tracker.

## The manager plugin

With `claude.management_panel` on, Giverny carries a Claude Code plugin, `giverny`, whose one skill is `manage`. Invoke it as `/giverny:manage`. It is a generic dispatcher. It plans the tasks with estimates (`giverny-manage plan`), spawns one subagent per task with the task's name in the spawn description, stamps `start` and `land`, and has each worker re-estimate its own row. It does not rely on an issue tracker. It sits beside a project's own `/manage` skill, if the project has one, because plugin skills are namespaced.

**How it is installed** (verified against Claude Code 2.1.283):

- The plugin is written as a local **directory marketplace** at `<config dir>/giverny/claude-plugin/` (next to `feeds/`). Its files are the marketplace manifest, the plugin manifest, `skills/manage/SKILL.md`, and three small `sh` launchers in `bin/`, each running `<this giverny binary> <command>`: `giverny-manage` (`manage`), `giverny-eta` (`eta`) and `giverny-hook` (`hook`). Only files whose bytes changed are rewritten, and it happens at each start with the pane on, so a moved or upgraded binary is picked up. The app writes it when it starts; the hook also rewrites `skills/manage/SKILL.md` (only that file, only when it is there and differs) from the binary it runs, at a session's start and on a prompt that asks to manage, so a binary rebuilt under a running app brings its skill text with it.
- Each account's `settings.json` gets two keys:
  ```json
  "extraKnownMarketplaces": { "giverny": { "source": { "source": "directory", "path": "<config dir>/giverny/claude-plugin" } } },
  "enabledPlugins": { "giverny@giverny": true }
  ```
  That is all Claude Code needs. There is no `claude plugin install` and no network. A directory marketplace is loaded straight from its directory at session start, not from a cache, so the next session runs what this binary wrote. The plugin's version is Giverny's own, so a Giverny upgrade updates the plugin. Sessions that were already running keep the skill they started with.
- `bin/` of an enabled plugin is on the `PATH` of the Bash tool, in the session and in its subagents, which is how the launchers are found.
- **The launchers run without a permission prompt.** A plugin cannot grant permissions (of its own `settings.json` Claude Code keeps only `agent` and `subagentStatusLine`, and a skill's `allowed-tools` lasts one turn of the session that ran it, never a worker's), so each account's `settings.json` also gets three rules at the end of `permissions.allow`: `Bash(giverny-manage:*)`, `Bash(giverny-eta:*)` and `Bash(giverny manage:*)`. Without them every worker's `eta`, `run` and `claim` stops and waits for a person. Only rules that are missing are added, and the user's own rules keep their order; a `permissions` or `allow` that is not an object or a list is left alone. Claude Code matches each part of a compound command on its own and needs no rule for read-only commands, so `giverny-manage eta … 2>&1 | tail -3` and `cd <dir in the project> && giverny-manage run …` pass. Turning the pane off removes these three rules with the plugin's keys.
- **The skill is a switch of its own.** `management_panel.manage_skill` (on by default) decides whether `skills/manage/SKILL.md` is in the plugin. Off, the next sync removes that file only: the plugin, its hook, its launchers and `/giverny:clear-done` stay, so the pane works as before, and `/giverny:manage` is gone from new sessions in every account. It follows the pane's consent rule: the plugin is written only where the pane's keys are.
- **A `SessionStart` hook only with names on.** With `management_panel.ask_names` on, `hooks/hooks.json` also runs `giverny-hook` on `SessionStart` (no matcher: a start, a resume, a `/clear`, a compaction); see **Session names**. Off, it is not there. A sync prunes any other file under `hooks/`, since the marketplace directory is Giverny's alone.
- **The hook**. `hooks/hooks.json` carries a `PostToolUse` hook (matcher `*`) running `"${CLAUDE_PLUGIN_ROOT}/bin/giverny-hook" 2>/dev/null || true`: right after a dispatcher starts a worker with no estimate it asks the dispatcher for one, and about five minutes into a worker's work it asks that worker, once, for a fresh estimate (see **Agent ETAs**, and **Writing it with `giverny manage`** for a task's row). The same hook delivers a manager's `ask`/`reply` messages and renews the calling session's ledger leases (see **Resources**). It exits 0 and prints nothing for every call that is not due anything, and reads no file for a call that is not a subagent's and has no message waiting: it parses only the payload's `session_id`, `agent_id`, `transcript_path` and `tool_name` (an `Agent` call's response is read too, for the worker it started), `stat`s the inbox, the ledger and the session's heartbeat marker (`resources/beats/<session>`, whose mtime is the last beat; the ledger is locked, read and maybe written only when that is 30 s old). Measured in-process, that is about 8 µs a call with a 20 KB tool response, of which ~4 µs is the three `stat`s; the process start (~5–7 ms for the `giverny` binary) is the whole cost that matters.
- **One manager session never reaches into another's work**. The same hook runs as a `PreToolUse` hook on Bash and on Edit, Write, MultiEdit and NotebookEdit, and refuses, naming the owner and pointing at `giverny-manage ask <task> "…"`: a `kill`/`pkill`/`killall` (or `kill $(pgrep …)`, `pgrep … | xargs kill`) of a process another live session owns; `systemctl --user stop|kill|restart|freeze` of its `giverny-run-*` or `giverny-claude-*` scope; a mutating git command (checkout/switch, reset, restore, stash, clean, commit, merge, rebase, `worktree remove|move`, `branch -D`, …) or an edit in a linked worktree another session's live worker works in (the cwd of its running `giverny manage run`, or of another live claude started there; the main checkout is everyone's); and `CLAUDE_CODE_SESSION_ID=<other> giverny-manage …`. A process's owner is its cgroup's scope — the tab's `giverny-claude-<pid>.scope`, whose claude's session is Claude Code's `sessions/<pid>.json`, or a run's `giverny-run-<task>-<pid>.scope`, whose `.live` record (else the ledger's lease) names session and task — which an orphan keeps, else the claude above it. Every `giverny-manage` command already acts on its caller's own rows and leases (a lease is `<session>:<task>`), and `--session <id>` of a session another live claude runs is refused for all but `show`, `path`, `resources` and `accuracy`. A `release` of a task another session holds says whose it is. What cannot be resolved — a pid in a variable, a regex beyond `.`, `.*`, `^`, `$`, a process with no claude above it, an owner whose claude (or run and lease) is gone — is allowed. Linux only.
- **The manager mark**. A session is a **manager** once the manage skill ran in it — never because it wrote rows, which any agent can do from a note to itself. The hook marks it: the `PostToolUse` hook sees the session's own `Skill` call with `giverny:manage` (or `manage`), and the `UserPromptSubmit` hook sees a prompt that starts `/giverny:manage`, which Claude Code expands into the skill with no `Skill` call. A subagent running the skill marks nobody. The mark lives beside the feeds: `<feed dir>/managers/<session>.json` (`{"session", "root"}`) and the same under `managers/roots/<root>.json`, keyed by the conversation's root as names are, so a resumed or compacted session (a new id, the same root) is found again and its mark copied under the new id; the pane also finds it under a tab's earlier ids. `/clear` starts a new conversation, which is no manager until the skill runs again. The mark opens a manager's pane before its first spawn and draws its Next up and build rows (rule 1 of **Merge**); `managers::is_manager` (also `manage::is_manager`) is the one question code asks.
- **"Manage this" runs the skill.** With the skill on, `hooks/hooks.json` also runs `giverny-hook` as a `UserPromptSubmit` hook. A prompt that asks to manage (an imperative "manage" at the start of a clause with work after it: "manage that task", "… and manage this plz", "can you manage these issues?", `/manage`) gets context telling Claude to invoke `giverny:manage` before anything else, over any project skill for orchestrating. A skill is otherwise picked only from its description, and "manage" reads as a plain verb. Questions and talk about managing ("how do I manage this?", "make sure they manage the resources"), "managing"/"manager", and quoted or pasted text do not fire it. Every other prompt gets nothing.

### Session names

With **Settings → Management panel → name every session** on (`management_panel.ask_names`, **off by default**), every Claude session in a Giverny tab has a full name, shown beside the model on its status line (`giverny statusline`) in the chrome's accent colour: `Opus 5.5 (Rotem Giverny)`.

- **Named at its start**. The plugin's `SessionStart` hook draws the session its name, records it and tells it in one line of context, before its first turn; a session that has a name already (a resume, a compaction) is told that one. **A `/clear` keeps the name**: the session it starts takes back the name and room of the one it cleared in the same tab, found by the tab's `GIVERNY_TAB_ID` (`names/tabs/<tab id>` holds the last session named there), unless another live session took that first name meanwhile; only the name and room carry over. A new name means a new tab, or a fresh `claude` in it. Only if recording fails is it told to run `giverny-manage name` instead. Only a Giverny tab's own session is named: never a subagent (a payload with `agent_id`), a background job's session, or a claude nested in a tab.
- **The name is Giverny's**. A session with no name is drawn a first name from Giverny's own list (a few hundred personal first names of many origins; sessions left to pick one kept picking the same few) at its start, or by `giverny-manage name` with no argument, and it is recorded and printed. **No two live sessions share a first name**: the draw skips the first names of sessions whose claude runs now, by Claude Code's own registry, so one comes free again once its session ends.
- **The surname is where the session was born**, as surnames once were: the name of the rail category its tab sits in, as written there with its first letter capitalised (`giverny` → `Rotem Giverny`, `MyApp` stays `MyApp`); spaces and odd characters become a hyphen (`side project` → `Side-project`), never a refusal. A tab's shell carries its category as `GIVERNY_CATEGORY`, set when the shell starts; a shell older than that is looked up by its `GIVERNY_TAB_ID` in the app's saved workspace (`state/tabs.json`, read only). With no category (outside a Giverny tab, a background job) the surname is the repo the session runs in, a worktree counting as its main checkout, else the directory's name. Not drawn, so two managers in one category are told apart by their first names; a full name may come again once its first holder has ended. **Fixed at birth**: moving or renaming the tab later renames nobody, and a resumed session keeps the name it had, one with an older drawn surname (`Rotem Ashby`) too.
- **Read it back** with the same `giverny-manage name`: once a session has a name it prints it and never draws again.
- **A name may still be given.** `giverny-manage name Tamsin` takes the category surname (`Tamsin Giverny`); a full name passed in (`name Pike Vance`, a revived session keeping its old one) is kept as given. Either is refused, naming the holder, when another live session holds that first name; the same session (or another id of its conversation) re-taking its own is fine. Naming again with the same first name keeps the surname already recorded, so nobody is renamed halfway through. A name is one or two words of letters, digits, hyphens and apostrophes.
- **A tab can be titled after it**. With **Settings → tabs & titles → name Claude tabs after their session** on (`rail.place_titles`, off by default), a named session's tab reads as its place on the rail: its first name and a room, `Rotem's Workshop`, `Fenn's Loft`. The room is drawn once per session from a short list when it is named, recorded beside the name, and comes with it across a resume, so the title holds. Claude's own title moves to the tab's hover; a title typed on the tab still wins; an unnamed session (or names off) keeps Claude's title.
- **`/resume` shows it**. Claude Code's `/resume` picker lists a session by the first of its agent name (`--name`), its custom title (`/rename`, `--name`), its AI title, a summary, and its last prompt (2.1.312). A named session's row reads `<Name> · <that text>` (`Rotem Giverny · Fix the login redirect`): the plugin's `Stop`, `SessionStart` and `SessionEnd` hooks append a `custom-title` line carrying the name and the text the row would show without it, in one `O_APPEND` write (the transcript is never rewritten), whenever the last one in the transcript's last 64 KiB (what the picker reads) is missing or no longer matches: the text appears with the first prompt and can move later, and the first turn's ~90 KB prompt snapshot, written after its `Stop`, pushes the title out of that window until the session's end appends it again. A title the person gave (`/rename`, `--name`: a custom title not starting with the session's name, or an agent name) is left alone, as are unnamed sessions. A running session does not take the line up, so its prompt box and terminal title are unchanged; a resumed one loads it as its title, so its terminal title (a tab's own title, unless typed or `rail.place_titles`) reads `Rotem Giverny · …` too. Text is cut to 120 characters.
- **Where it lives.** `<feed dir>/names/<session>.json` (`{"session", "name", "room", "root"}`; a document from before rooms is given one the first time it is needed), and the same under `names/roots/<root>.json`, keyed by the conversation's root (the uuid of its transcript's first turn, which Claude Code carries across a re-id). A session that only names itself writes no feed and is no manager: no rows, nothing in the pane. A resumed session has a new id but the same root, so its status line finds the name by the root and records it under the new id. A feed's `name` (from before names had their own home) is still shown for its session.
- **The switch is a file.** `<feed dir>/names/on` exists while the switch is on and the pane is on; Giverny writes and removes it. Off, no session is asked, managers included, and no status line shows a name.

**The house rules**, the same ones `subagentStatusLine` follows:

- **On by default, written only where the account opted in.** `claude.management_panel` defaults to on and sits at the top of Settings → Management panel. The keys go only into an account whose `settings.json` holds Giverny's hooks (installed from the banner's click); an account without them is left byte-identical. Turned off, nothing is written.
- **Never over someone else's.** A marketplace called `giverny` that does not point at a `giverny/claude-plugin` directory is left alone. The plugin is then not installed on that account, and the settings log says so.
- **A user's `disable` stands.** If `enabledPlugins["giverny@giverny"]` is already `false` (`claude plugin disable`), it stays `false`.
- **Removed when the pane goes off.** Both keys go, and a map we emptied goes with them. Claude Code's own record of the marketplace (`plugins/known_marketplaces.json`) loses its `giverny` entry, as `claude plugin marketplace remove` would do. The `claude-plugin` directory is deleted. `uninstall_from` takes the keys too.
- **A no-op writes nothing.** If Giverny is deleted without turning the pane off, Claude Code finds the directory missing and skips the plugin silently.

## Where the live rows come from: the relay

With `claude.management_panel` on, Giverny installs one key into each account's `settings.json`:

```json
"subagentStatusLine": { "type": "command", "command": "<giverny> relay --subagent-line" }
```

Claude Code runs that command at least every five seconds while a session has live workers. It passes the worker list on stdin: `session_id` and `tasks[]`. The relay forwards that list to the app, tagged with the tab it ran in (`GIVERNY_TAB_ID`, which reaches this command). It then prints one `{"id":"<task id>","content":""}` line per task. An empty decoration hides that row of Claude Code's own subagent panel. With every row hidden, the whole panel is gone, `● main` included. A brand-new worker may show for one tick (~300 ms) before it is hidden.

- **Outside a Giverny tab** (no `GIVERNY_TAB_ID`), the relay forwards nothing and prints nothing, so Claude Code draws its panel as usual.
- **In a session that is not the tab's own**, the relay does the same. A `claude` started inside the tab's claude, or under a `tmux` the tab launched, inherits `GIVERNY_TAB_ID` too. The tab also exports the app's process id (`GIVERNY_PID`), and the relay walks up from itself: the tab's own claude reaches the app with no other `claude` on the way. A nested one passes a second `claude`, and a multiplexer's sessions never reach the app at all, so they keep their own panel and their workers stay out of the tab's pane. The plain hook relay applies the same check, so a nested session does not move the tab's state or its resume target either. Where the walk sees no `claude` at all (a relay run on the Windows side for a session inside WSL), it trusts `GIVERNY_TAB_ID` as before.
- **Only in an account that opted in.** The setting is on by default, but Giverny writes the key (and the plugin's keys) only into an account whose `settings.json` already holds Giverny's hooks — installing them is the consent, as it is for the live-usage statusline. Installing the hooks brings the key with them. An account without them is never written to: following the setting at startup is a no-op for it, down to the bytes.
- **With the setting off**, Giverny removes the key again, and the relay prints nothing even where the key is still there.
- **Uninstalling the hooks** (`hooks::uninstall_from`) removes the key too, since it is the same relay.
- **An account whose `subagentStatusLine` is someone else's** is left alone: the installer never replaces a command it did not write. On that account the pane gets no live rows.
- **Project settings override user settings.** A project that sets its own `subagentStatusLine` shadows Giverny's. To keep both, that command must pass through. Inside a Giverny tab (`GIVERNY_TAB_ID` set), pipe the stdin it received, byte for byte, into `giverny relay --subagent-line`, and print that command's stdout as its own. It must not add decorations of its own for ids the relay hid.

## Known limits

- **`giverny manage run` caps by the kernel only on Linux with a user systemd.** On macOS Giverny holds it itself, from a sampler (**On macOS Giverny holds the limits itself**, above, with its gaps), and its memory peak is the tree's as the guard saw it four times a second. Elsewhere — Windows, a container, Linux with no user systemd — the command runs uncapped, the lease is advisory, and its memory peak is the largest single process's, not the whole tree's. On Windows two `run`s under one lease do not take its slots in turn (there is no slot lock there). macOS has been type-checked (`aarch64-apple-darwin`) and the holding tested on Linux under `GIVERNY_RUN_NO_SYSTEMD=1`, not on a Mac.
- **The tab cap has gaps.** A claude is taken within a second of starting, so what it started and detached before then stays outside, and a command forked in the first second before the sampler raises its `oom_score_adj` keeps 0 until the next pass (its own size still makes a big runaway the OOM killer's pick). The Bash guard reads the command's text: a command built at run time (`$(echo … | base64 -d)`), one a script file or a program starts, work handed to a `tmux` server started elsewhere, or to Windows through WSL interop (`cmd.exe`, `powershell.exe`, which run outside Linux cgroups entirely) is not seen; the sampler's sweep finds afterwards only what stays under the user manager with a tab's environment. Both remind, neither refuses: what holds is the slice's memory cap.
- **The reach guard sees what the text and `/proc` say.** A worker of another session working in a worktree with no `run` going and no claude of its own started there is not seen there; a kill by a script or a program, or a pid computed at run time, is not seen either. Off Linux nothing is refused.
- **A plain `run` shows no live use.** Without a systemd scope there is no cgroup to read, so the pane's use column stays empty while the command runs; its peak and CPU time appear once it ends.
- **An `ask` waits for its manager's next own tool call.** A manager blocked in a long tool call (waiting on its workers, say) does not see it until that call returns.
- **An `ask` is addressed by session id.** One sent to a session that has since been re-id'd (`/clear`, a compaction) never arrives.
- **The `giverny` plugin is Unix-only.** Its launchers (`giverny-manage`, `giverny-eta`, `giverny-hook`) are `#!/bin/sh` scripts, which native-Windows Claude Code cannot run, so a Windows build writes no plugin directory and no `extraKnownMarketplaces`/`enabledPlugins` keys, and takes back the ones an older build wrote. The panel's live rows (the subagent line) still work there; the manage skill, its hooks, ETAs and `/giverny:clear-done` do not. A Claude inside WSL gets them from a Giverny built for Linux.
- **A held lease does not grow.** `claim` only shrinks one in place; to grow it, release it and claim again, which gives up its place in the queue.

## Versioning

- `version` is bumped **only for an incompatible change** — a field whose meaning or type changes, or a new field a reader must understand to draw the table correctly.
- **Adding** a field is not a bump. Readers ignore fields they do not know, so a writer may send more than this page lists.
- A feed whose `version` is **greater** than the reader's is ignored entirely (the pane shows only the live rows) rather than half-understood. A missing `version` is read as `1`.
- The only things that make Giverny ignore a whole file are: it is not JSON, it is not a JSON object, or its `version` is too new. Anything smaller costs that field (a wrong type reads as absent) or that row (no usable `stage`, or neither `key` nor `agent_id`).

## Checklist for a writer

(`giverny manage` does all of this. The list is for writers of your own.)

- [ ] Path: `${GIVERNY_FEED_DIR:-<config>/giverny/feeds}/<parent session id>.json`, directory created if missing.
- [ ] Write to a non-`.json` temp name in the same directory, then rename.
- [ ] `"version": 1`, `"session"`, and every earlier id in `"aliases"`.
- [ ] Each row has `stage` and `key`; `agent_id` wherever a worker holds it.
- [ ] Timestamps RFC 3339 or epoch ms; `eta_s` in seconds from `started`.
- [ ] Done rows: `ended` (and `eta_delta_s` only when you know better).
- [ ] Rewrite on change, not on every tick.
